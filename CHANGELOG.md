# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
Release notes on GitHub are generated from the section for each version.

## [Unreleased]

### Fixed

- **`scripts/vegaduta personal --minimal` (and `--no-valkey`) no longer exits in silence.** The Valkey step ended with a test that returns failure when Valkey is off, and under `set -e` that stopped the whole run before it printed its plan or started anything. `tests/install` now covers it.
- **SDK artifacts now ship the license they declare.** Every `io.github.cd-lc:*` jar carried the repository's BSL-1.1 `LICENSE`/`NOTICE` in `META-INF` while its POM declares Apache-2.0; the `sdk/` subtree now has its own Apache-2.0 `LICENSE` and `NOTICE` (also copied into the Python and TypeScript package directories), and the jars bundle those.
- **`ApprovalNotificationBlockedException` is a `GovernanceException` again.** It extended `RuntimeException`, so `catch (GovernanceException)` - the documented one-stop handler - missed it.
- **Preparing an install no longer stops another install's containers.** When the launcher found the data of an earlier personal install in Docker, `scripts/vegaduta secrets`, a dry run and the install tests all ran `docker stop` on every container of the default `vegaduta-personal` project. The name of the new project is still chosen then, but containers are stopped only on a real start, and only one that publishes a host port the new install needs.
- **The personal install test no longer overwrites your real kept secrets.** `tests/install/vegaduta-personal.test.sh` did not set `VEGADUTA_SECRETS_KEEP`, so each run replaced `~/.config/vegaduta/secrets.env` with throwaway secrets. It now keeps its own copy, and a fake `docker` checks that file-only runs never stop or remove a container.
- **REST clients: streams, retries and errors are publish-grade.** The Python client's 60 s request timeout also applied to SSE reads, so a stream idle for a minute died; `stream()` now bounds connect+headers only (`http.client`, blocking reads). Both clients retry idempotent GET/HEAD on 429/5xx/network failures honouring `Retry-After`, re-resolve a callable token once on 401, wrap transport failures in a `NetworkError`, expose `code`, `headers` and `retry_after`/`retryAfterMs` on `ApiError`, and send an SDK `User-Agent`. The TypeScript client gains `timeoutMs` (client and per-call), `maxRetries` and `userAgent` options.
- **The core image is about 340 MB smaller.** The application jar was copied as root and then rewritten by a recursive `chown`, so it was stored in two layers. It is now copied with its owner set.
- **SDK metadata is publish-ready.** `vegaduta-agent` uses PEP 639 license metadata and carries `LICENSE`, coverage and mypy config and the missing `Security`/`OS Independent`/`Typed` classifiers; `vegaduta-sdk` (Python) gains full PyPI metadata; `vegaduta-sdk` (TypeScript) gains `exports`, `repository`/`bugs`/`keywords`, a `prepack` typecheck+build, a pinned `typescript` devDependency and a package `README.md`.

### Added

- **A release path for the generated REST clients.** `.github/workflows/rest-sdk-release.yml` verifies, builds, attests and publishes the npm and PyPI `vegaduta-sdk` packages for `restsdk-v*` tags (publish stays off until `SDK_PUBLISH_NPM`/`SDK_PUBLISH_PYPI` are set); setup and procedure in `docs/maintainers/releasing-rest-sdks.md`. New tests cover the classification package (lethal-trifecta detector, resolver overrides, composite and annotated sources) and the Spring AI wiring, plus the retry/timeout/error paths in both REST runtimes.

## [0.1.9] - 2026-10-21

### Added

- **Conversations follow you.** `GET /api/chat/threads` lists the signed-in user's chat sessions (title, agent, last activity) and `DELETE /api/chat/threads/{agentId}/{sessionId}` removes one; the Assistant merges them into its thread list, so history shows on a new browser or device. Needs `APP_CHAT_BRANCHING_ENABLED=true` (404 otherwise; the console then keeps its local list). The Assistant now records its turns in the conversation tree, and reopening a thread older than the 24 h session window reads the stored tree.

### Fixed

- **Service and database images clear the release's critical-vulnerability gate again.** Two advisories published after v0.1.8 stopped the v0.1.9 image scan: Pillow 12.3.0 (critical GHSA-8g5g-8vmr-9782, fixed only in 13.0.0) in the sidecar, voice-agent and code-intel images, and certifi 2026.10.18 inside the CloudNativePG base of the `postgres:16-pgvector-age` image. Pillow is now 13.0.0 in all three; code-intel needs `services/code-intel/overrides.txt` for that, since fastembed caps Pillow below 13 although code-intel only uses its text embeddings, and so installs its lock with `--no-deps`. The CNPG image replaces its certifi with the hash-pinned 2026.10.19 wheel at build time (`deploy/postgres/replace-certifi.py`), because its pip is removed upstream.
- **Service images carry certifi 2026.10.19.** certifi 2026.7.22, pinned in the app-builder, code-intel, rl-trainer, sidecar and voice-agent locks, has a critical advisory (GHSA-6q48-6c7w-9gw2) published after v0.1.8, and the release's image scan stopped on it. The five locks now pin 2026.10.19; nothing else changes.
- **WhatsApp QR messages are no longer split between processes.** The jobs and worker shapes ran a second WhatsApp QR receiver next to the API's, so on a full install with the bridge each took a share of a linked number's incoming messages. They now switch it off, like the Signal receiver (`app.whatsappqr.receive.enabled: false` in `application-jobs.yml` and `application-worker.yml`).
- **The chat artifacts directive keys sit where the code reads them.** The `artifacts` block in `application.yml` was nested under `app.chat.branching`, where nothing reads it; it now sits under `app.chat.directives`. Defaults and the `APP_CHAT_DIRECTIVES_ARTIFACTS_*` variables are unchanged.
- **A personal install keeps chat history.** The 0.1.8 note said personal installs already had it on; they did not: `personal.yml` never set `APP_CHAT_BRANCHING_ENABLED` and core defaults it to off, so the Assistant's history stayed in one browser and a conversation expired after 24 h. The `personal` profile now turns it on (`app.chat.branching.enabled`, still `APP_CHAT_BRANCHING_ENABLED=false` in `deploy/compose/core.env` to switch it off). Conversations that had already expired are not recovered.
- **A personal install's local model answers again by itself after a secrets change.** When the install kept its database but got a new `.env` (a re-install, or a repaired install), the local model's platform-pool entry was still listed as "in use" while every chat answered "No platform LLM is configured": its stored key no longer decrypted under the new `APP_ENCRYPTION_KEY`, so the chat path left it out. Core now repairs that entry (re-keys it, re-enables it, switches the pool back on) at every start and, when a chat still finds the pool empty, on the spot during that chat. The troubleshoot page says why the entry cannot be used instead of calling it in use, and the chat notice points to Troubleshoot.
- **Windows: the personal install no longer stops with "required variable WORKSPACE_RUNNER_SECRET is missing a value".** The PowerShell launcher (`scripts/vegaduta.ps1`, which the Setup app runs on Windows) generated a shorter list of secrets than `scripts/vegaduta`: it lacked `WORKSPACE_RUNNER_SECRET`, which `personal.yml` and `lite.yml` require, and `SEARXNG_SECRET`, which web search requires. It now generates both, and an existing install gets them on its next start. A test fails CI when the two lists differ again.
- **No secret a compose file requires can stop an install again.** Both launchers (`scripts/vegaduta`, `scripts/vegaduta.ps1`) now generate every secret-like variable any file under `deploy/compose` marks as required (so the opt-in WhatsApp QR and DefectDojo overlays no longer need hand-made secrets), not only the ones in their own table; and before `up`, each asks Docker Compose itself what is still missing and fills it, stopping with a plain "set X in .env" only for a value that is not a secret. The PowerShell launcher also no longer crashes on a Compose error written to stderr while it checks the database password. `tests/install` covers all three paths.

## [0.1.8] - 2026-10-21

### Fixed

- **The first chat no longer waits for the platform model to wake up.** A hosted model that scales to zero took 70 s or more to answer the first message. The console now asks core to load it (`POST /api/platform-llm/warm`, a one-token request to the pool's top row, at most once every 4 minutes per core instance) as soon as someone signs in or opens a chat. If a reply still has not started after 8 seconds, the chat says the model is starting up and that later replies are fast. Off with `APP_PLATFORM_LLM_WARM_ENABLED=false`.

### Changed

- **Chat history is kept by default on full installs and in the Helm chart.** `APP_CHAT_BRANCHING_ENABLED` now defaults to `true` in `deploy/compose/docker-compose.yml` (lite and personal already had it) and the chart gains `core.branchingEnabled` (default `true`), so each message is stored in Postgres for 30 days instead of expiring from Redis after 24 h. Conversations that had already expired are not recovered. Set it to `false` to go back.
- **Local models answer sooner.** The Compose `local-ai` overlay now loads the model when the stack starts and keeps it in memory (`OLLAMA_KEEP_ALIVE=-1`, `OLLAMA_FLASH_ATTENTION=1`), so the first reply no longer pays a cold start, and sends `reasoning_effort: none` so reasoning models skip their hidden thinking pass (`LOCAL_LLM_REASONING_EFFORT` changes it; new core property `app.llm.ollama.reasoning-effort`, blank by default outside the overlay). The Assistant shows a short note when it runs on a local model, with a link to Agent settings where it can be tuned for speed or quality.
- **Academy links everywhere, Academy source nowhere.** The Academy is a separate, proprietary deployable, so the open-source console links to it but carries none of its content: the in-console `/learn` index, the screen→lesson map (`consoleLessonMap.ts`), the curriculum index and every lesson-id deep link are removed, and per-screen "Learn this" buttons become plain links to the Academy. The OSS landing header and footer, the docs site nav and every tier's compose/Helm defaults point at the hosted `academy.vegaduta.ai` (`WEB_ACADEMY_URL`/`NEXT_PUBLIC_ACADEMY_URL`, still overridable; `""` hides the links on a fork). The personal tutor stays at `/learn/tutor`.

## [0.1.7] - 2026-10-21

### Fixed

- **Windows Setup no longer fails with "A required privilege is not held by the client".** The release package carried one symlink (`deploy/models/catalog.txt`), which Windows only lets administrators or Developer Mode create, so Setup stopped while unpacking. The release now ships the file itself, and Setup copies the file whenever the system refuses a symlink.
- **A database left by an earlier install no longer stops the start.** Installing into a new folder generates a new database password, but the data volume kept the earlier install's one, so `db-roles` failed ("password authentication failed", exit 2) and nothing came up. `personal` and `up` (bash and PowerShell) now notice this, set the database to this install's password (the data is kept) and start again.
- **Re-installing never locks you out of your own data.** The install's secrets (database passwords, `APP_ENCRYPTION_KEY`) are also kept outside the install folder (`~/.config/vegaduta/secrets.env`, `%LOCALAPPDATA%\VegaDuta\secrets.env` on Windows and WSL), so a new folder reuses them. When Docker holds an earlier install's data and no copy exists, that data is left untouched and the new install starts under its own project (`VEGADUTA_PERSONAL_PROJECT`).
- **Windows: re-running Setup with VegaDūta already running works.** The personal checks no longer fail on ports 3000/8080 held by VegaDūta's own containers, use `WEB_HOST_PORT`/`CORE_HOST_PORT`, and also catch ports Windows reserves (Hyper-V/WinNAT), which look free but cannot be used. Setup stops with the fix instead of retrying a port conflict three times.
- **Windows: personal installs get Valkey and the tools runner, as on macOS/Linux.** `vegaduta.ps1` now adds the `valkey` profile and, with the Tools or Browser add-on, routes STDIO connectors to `mcp-stdio-runner`.
- **A failed model download no longer stalls the install for an hour.** The Ollama container retries the download and restarts after five failures instead of staying up but never healthy.

## [0.1.6] - 2026-10-20

### Fixed

- **The local model follows Ollama when it moves.** Installing Ollama on the computer after an install that used the Ollama container now switches `personal` to it (Windows and macOS/Linux launchers) instead of keeping the container, and core repoints its own "Local model (Ollama)" pool row to the new address and model. Before, the row kept calling the old Ollama, so the console showed a local model in use while every chat failed. A row whose model is not on its Ollama (never pulled, or removed) switches to the configured model when that one is there, and an Ollama that is installed but not running (after a restart, or its app was closed) is started; if it still does not answer, the container takes over.
- **No GPU, no GPU mode.** Docker on WSL2 lists the nvidia runtime even on a laptop without a graphics card, which switched the Ollama container to GPU mode and made it fail to start ("no adapters were found"). The GPU overlay is now used only when `nvidia-smi` reports an adapter.
- **Installing from a checkout or a download of `main` just works.** An empty `VEGADUTA_VERSION` used to stop `personal` with an error; it now uses the latest published release and records it in `.env`.

### Changed

- **The local model's context window follows Docker's memory.** Under 6 GB the container model runs with an 8192-token window, under 10 GB 16384, otherwise the 32768 default (`LOCAL_LLM_NUM_CTX` overrides), so a small laptop is not pushed into out-of-memory kills by the model's working memory.
- **Local AI stays the default on small machines.** `personal` no longer drops to the cloud-key path below 8 GB of RAM: it picks the smallest catalog model (CPU only is fine) and warns that the first reply is slow; only machines under 4 GB keep the cloud-key path. The model is now sized to the memory Docker actually has when it runs in the Ollama container (a WSL2 or Docker Desktop VM is often much smaller than the machine), with a hint to raise Docker's memory for a bigger one. `--local-ai` given by hand now gets a model sized the same way instead of Docker's `qwen3.5:4b` default, and under WSL2 the script offers (with a yes, a backup and the one restart step) to give Docker 8 GB through `%UserProfile%\.wslconfig`.

## [0.1.5] - 2026-10-20

### Changed

- **Personal installs come with a free local model.** `personal` (bash and `vegaduta.ps1`, so the Setup app too) now picks the model that fits the machine's RAM from the shared catalog and downloads it without asking: free open-weights models, no account or subscription. On macOS (Homebrew) and Windows (`winget`, per-user) Ollama itself is installed and started when missing, so the model runs natively and can use the GPU; Linux and WSL, and any failed install, use the Ollama container. Previously it only adopted an Ollama that was already installed, so most machines ended up with no model. `--cloud` (`-Cloud`) opts out and is remembered; machines under 8 GB of RAM keep the cloud-key path; installs that never chose get the model on their next run. The first start waits up to an hour for the download, and the Setup app gives Docker room for the model.

### Changed

- **Setup app repairs the machine instead of stopping.** Clicking Install now installs Docker Desktop (silently accepting its licence, so no first-launch screen), starts it, turns on WSL2 on Windows (one permission prompt; after a required restart Setup reopens by itself), gives Docker's WSL2 VM enough memory through `%USERPROFILE%\.wslconfig` when the computer can spare it, and turns on Docker's start-at-sign-in so the stack returns after a reboot. A failed start is classified (stale registry login, full disk, stopped engine, interrupted download, slow first boot), repaired and retried up to three times. Missing or stopped Docker no longer blocks the Install button. The setup app also accepts the `SHA256SUMS.txt` asset name used by v0.1.0.
- **Merged landing page and release-aware public copy.** The signed-out homepage keeps the OSS landing's technical spine (capabilities, standards, SDK-as-dependency, install paths) under the marketing chrome (ambient backdrop, display typeface), and adds direct "Download the release" and "Try it live" calls to action. Install instructions now use the signed release artifacts (desktop installers, pinned GHCR images, the published Helm chart) instead of a source build, and every public license mention follows the Business Source License 1.1 relicensing (SDK stays Apache-2.0).
- **Tenant surfaces stop offering server-side controls.** On a full install (`NEXT_PUBLIC_DEPLOY_ENV=full`) `/add-ons` leaves the rail and renders an "all add-ons included" notice instead of switches, since every extra already ships. The local-model wizard (`/providers/local-model`), its entry points on `/providers`, the local-model card on `/troubleshoot` and the Assistant's model warm-up are now personal-install only (`localModelAllowed`) — on lite and full the LLM pools are operator-managed infrastructure a tenant can browse but not change.

### Security

- **Browser images ship the current stable Chrome.** core-full and mcp-stdio-runner-browser install Chrome-for-Testing stable at build time (behind a fixed `current` path for `PUPPETEER_LAUNCH_OPTIONS`) and drop the Chrome 131 builds puppeteer@23.11.1 downloads for itself, so the release image scan no longer fails on fixed critical CVEs.
- **Release images move off Debian bookworm.** Node services to `*-trixie-slim` (22.23.3 / 24.21.0), Python services to `3.12.15-slim-trixie`, the JRE to `eclipse-temurin:21.0.12.1_1-*-noble`, PostgreSQL to `postgres:16.15-trixie` and CloudNativePG to `16.15-system-trixie`. The release's critical-vulnerability gate now fails only where a fixed package exists (`only-fixed`), and `.grype.yaml` records the scoped wont-fix exceptions (re-matched automatically the day Debian ships a backport).

### Changed

- **The OSS landing now sells the whole suite.** `/` leads with three ways in - run the platform (Personal, Lite, Full, Kubernetes), build on the SDKs (Java, Python, REST clients), extend with plugins and apps (IDEs, browsers, mobile, MCP) - plus a "Get VegaDūta" section with per-OS installer cards, the terminal installer, Helm and the verification step.

### Fixed

- **Downloads page shows the brand name correctly.** Headings use the `BrandName` wordmark (orange "Dūta") instead of plain text.

## [0.1.4] - 2026-10-19
### Changed

- **License: Business Source License 1.1.** The platform (everything outside `sdk/`) is now under BSL-1.1: free for any use except offering the software itself to third parties as a competing hosted service, and each version converts to Apache-2.0 four years after its release. The `sdk/` directory stays Apache-2.0 so clients embed anywhere. Versions already released under Apache-2.0 remain under Apache-2.0.

### Added

- **Assistant on every install.** `/assistant` is no longer personal-only: the rail lists it on lite and full too, and each person keeps their own Assistant agent (the lookup no longer adopts a teammate's shared agent that happens to be named "Assistant"). `/add-ons` also appears on lite, where its commands now render as `scripts/vegaduta up --lite ...`; the full stack keeps it off the rail (its service set is fixed at deploy time).
- **Lite: the single-box add-ons work on `up --lite`.** `--profile tools` runs STDIO MCP connectors in a new `mcp-stdio-runner` container (its own network, no published port, no volumes), `--profile workspace` adds `workspace-runner` and the Assistant's projects folder (`VEGADUTA_PROJECTS_DIR`), and `--browser` layers the browser-runner overlay. Lite ships the Assistant's features on (routines, editable/persistent threads, resumable answers, data tables, learned skills and proposals) — each is an env switch away; without `--profile rag` core now reports the sidecar honestly off instead of failing calls to a missing host, and `APP_EMBEDDINGS_PROVIDER=auto` lets a cloud key or local Ollama serve embeddings.
- **Full: the recent feature flags are wired.** `SCHEDULED_TASKS_ENABLED`, `APP_CHAT_BRANCHING_ENABLED`, `APP_CHAT_RESUMABLE_STREAMS_ENABLED(+_STORE)`, `DATA_TABLES_ENABLED`, `APP_SKILLS_LEARNING_ENABLED`, `APP_LEARNING_PROPOSALS_ENABLED`, `BROWSER_V2/PROFILES/TAKEOVER_ENABLED`, `APP_ADDONS_TENANT_ADMIN_MAY_CHANGE` and `APP_ADDONS_HOST_TOKEN` now pass through `.env` (all keep their shipped-off defaults; core.env remains the escape hatch for the rest).
- **Realm reconcile runs on every boot, not only via the CLI.** Keycloak's realm import does not substitute `${env.*}` inside a client `secret`, so the `agentic-ai-core` client lands with the literal placeholder and every Keycloak admin call (tenant signup included) answers 401 until `reconcile-realm.kcadm.sh` runs. A new one-shot `keycloak-reconcile` service (lite and full) shares keycloak's network namespace, waits for it healthy, and runs the same script — a plain `docker compose up` now converges too.
- **Tier-aware setup guidance.** The Ollama-unreachable message, the local-model troubleshoot page and the browser-add-on empty state name the command for the install's shape (`scripts/vegaduta personal --local-ai=host`, `up --lite ...`, `up --full ...`) instead of always `personal`.
- **`/downloads`: a public page listing the latest release's artifacts.** The Setup-app cards (macOS .dmg, Windows .zip, Linux tarballs), the `curl | sh` installer, the source tarball, SHA256SUMS + sigstore bundle, GHCR images and the Helm chart all link to real release assets (the versioned dmg name can never be guessed), resolved from the GitHub releases API server-side and cached an hour. With no release yet the cards fall back to the releases tab and the page says so. Linked from the OSS landing nav and footer; the route is public.
- **Add-ons on every tier, with honest switches.** `/add-ons` is no longer hidden on the full stack: the overview now carries `mayChange` (the caller's AddonAccess verdict) so the console disables the switches for a caller who cannot change the set instead of letting the click 403, entries the full launcher cannot run (`rag`, `workspace`) are marked "not available on this installation tier", the apply command drops them, `enable` refuses them (`not_available`), and `--browser` renders as `--profile browser` (the full stack's runner swap, not the single-box overlay).
- **Personal: `--minimal` and `--no-valkey` for the smallest stack.** `scripts/vegaduta personal --minimal` runs just `postgres` + `core` + `web` (no SearXNG, no MCP runner, no Valkey, no browser); `--no-valkey` / `VEGADUTA_VALKEY=0` drops only Valkey and keeps the rest. Without the store, core's rate limits, budget windows and spend counters run in the bounded in-process fallback (`LocalRateLimitFallback`) — still enforced, still fail-closed; the choice is remembered in `.vegaduta-state`. Lite/Full keep Valkey always on.
- **Omnibus image: the personal tier in one container.** `ghcr.io/cd-lc/omnibus:<version>` carries PostgreSQL (pgvector + Apache AGE), a Redis-protocol store, core and the console behind one `docker run`; the release workflow builds it after the per-service images publish and signs it like the rest. Data and generated secrets live under `/data`. Tradeoffs: docs/personal-mode.md, "One container".
- **Slimmer image options.** `core/Dockerfile` accepts `--build-arg JRE=jlink` for a jlink-minimal runtime (same jammy base, ~half the Java footprint; the omnibus image uses it), and `deploy/postgres/Dockerfile.alpine` builds the same pgvector + Apache AGE extensions on `postgres:16-alpine` for size-sensitive installs.

### Fixed

- **Redis-backed counters no longer stall when the store is down.** After one failed Redis call, `RedisFixedWindowCounter` skips Redis for ~10 s instead of paying a connect timeout on every request before the in-process fallback engages — the same path `--no-valkey` installs depend on.
- **CI and security-scan pipeline.** The license scan pins the ScanCode 32.5.0
  toolchain stack it was released against, SARIF uploads (Trivy, OWASP ZAP,
  grype) now skip cleanly on repositories without code scanning enabled, the
  web typecheck job gets a larger Node heap, the internal-reference lint
  baseline is fully drained, and the docs-link gate passes again.

## [0.1.3] - 2026-10-19

### Added

- **Scheduled tasks: Signal, Matrix and iMessage delivery.** A task's result can now land on the personal-mode channels too, with the same approval gate, per-channel recipient validation and in-app fallback as the existing channels; the console form lists them. `SCHEDULED_TASKS_DELIVERY_CHANNELS` defaults to all channels on.
- **Chat-first personal install.** On a one-person (local-auth) install `/` lands on the Assistant (`/assistant`) instead of the Build Studio — the chat is the product there.
- **Browser device node.** `DevicePlatform.WEB` + `POST /api/devices/capabilities` + a `capabilities` column (V660): a paired device now declares what it can do. The new public `/device` page turns any browser into a device node — claim a pairing code, declare its honest browser capabilities (camera still, geolocation, notifications, clipboard, one-shot screen share, vibration), then execute queued commands (`GET_LOCATION`, `CAPTURE_PHOTO`, `SCREENSHOT`, `NOTIFY`, `VIBRATE`, `CLIPBOARD_*`) through the platform's own permission prompts. Add to Home Screen to keep it alive.
- **Scheduled tasks: `a2a` delivery.** A task can deliver its result to an external A2A-speaking agent (card URL as the recipient) through the new `A2aDeliveryPort` — the same operator allow-list, SSRF guard and signed-card verification as the `a2a_call_agent` tool, so an external agent gateway can act as the last mile for proactive messages.
- **Scheduled tasks: `voice` delivery.** A task can place an outbound phone call that speaks its result through the new `VoiceDeliveryPort` on top of the tenant's voice credential (Twilio today), trimmed to ~900 characters.
- **Setup app packaging.** New `installer/package.sh` builds the downloadable artifacts reproducibly: a universal `VegaDuta Setup.app` in a `.dmg` on macOS (optional `--payload` embeds the release tarball for a fully offline install, `--web-port`/`--core-port` stamp the launcher's ports), a Windows zip whose exe ships with a `READ-ME-FIRST.txt` explaining SmartScreen's "More info → Run anyway", and Linux tarballs with a README. `release.yml` gains a `setup-pkg-darwin` job so the `.dmg` is a release asset covered by `SHA256SUMS`; `installer.yml` can produce it on manual dispatch. Still unsigned - Gatekeeper/SmartScreen warn once and the READMEs say what to click.
- **Personal: the Assistant's browser as a light add-on.** `scripts/vegaduta personal --browser` (PowerShell `-Profile browser`; `--no-browser` turns it off) adds one `browser-runner` container (`services/browser-runner`, a Playwright 1.49.0 server with Chromium, `deploy/compose/browser.yml`) that the slim core attaches to with `app.browseruse.remote-url` (`APP_BROWSERUSE_REMOTE_URL`), instead of the 6 GB `core-full` image. The runner publishes no port, drops all capabilities, has a read-only root and a 2 GB limit, and sits on a network shared only with core. The Browser button and `GET /api/browser/automation/capabilities` report an unreachable add-on with its address. Verified with slim core plus the runner on a live stack and with `BrowserRemoteRealTest` (opt-in, set `BROWSER_REMOTE_URL`): navigate, read, screenshot, click and the private-address refusal against a real Chromium.
- **Personal: sign in without an e-mail address and password.** Passkeys (Touch ID, Windows Hello, a phone or a security key), a **PIN** of 6 to 12 digits that works only together with a secret stored in the browser you set it up in (ten wrong PINs revoke that browser), and one-time **recovery codes** now sit alongside passwords. First-run and invite setup can finish with a passkey or a PIN instead of a password; the account then has no password at all and shows 8 recovery codes once. The sign-in screen leads with a passkey button and a PIN pad and asks for no e-mail address unless you choose a password. **Account security** (`/login?security=1`) adds or removes passkeys and PIN devices and makes new recovery codes; these changes need a sign-in from the last 10 minutes, and the last way in cannot be removed. Passkeys need HTTPS on a real host name or `http://localhost`: an IP address cannot use them, and a changed host name invalidates them. New migration V655, `app.auth.local.passkey.origins` to limit the allowed addresses. Tested with a software authenticator and in component tests; not yet tried with a real passkey or in a browser.
- **Personal: web search and connectors are on from the first start.** A fresh personal install starts private web search (SearXNG, no API key) and the connector runner, and registers three pinned starter connectors: `fetch` and `time` (on) and `sequential-thinking` (off). ### Fixed

- **Setup wizard: a failed install can be retried and shows live progress.** Clicking Install after a failure did nothing visible - the run guard allowed only one install per process, and the event stream replayed the old error, which the page treated as terminal. Runs are now restartable once finished or failed, the event history resets for a new run, a `begin` event clears stale UI in every open tab, and the page shows a step strip (Download → Install files → Configure → Start containers → Finish), a spinner with elapsed time, a real download percentage (with an indeterminate bar when the server sent no length), a "Try again"/"Back" choice on failure, and an "already running" state instead of silence. Ticked extras are highlighted and the install button counts them.
- **Security: the Setup wizard no longer accepts commands from a web page.** The installer's loopback API (`/api/install`, `/api/docker/*`) previously took any POST - including a `text/plain` fetch a malicious site can send without a CORS preflight - while the wizard was open on a fixed port. It now mints a per-process token, puts it in the wizard URL, requires `Authorization: Bearer` on every `/api/*` call, and refuses requests whose `Host` header is not loopback.
- **Security: release extraction cannot write outside the install directory.** `unpackRelease` rejected `../` path members but not a tar symlink whose target escaped the dir (a `a -> /etc` member followed by `a/x`). Link targets are now confinement-checked and every write resolves through the symlinks already on disk against the resolved install root.
- **Security: the desktop-agent bearer check is timing-safe** (`crypto.timingSafeEqual`, like the sibling sidecars).
- **Security: every public-facing outbound HTTP call resolves through the SSRF guard.** A new `GuardedJdkHttpClient` drops in for `java.net.http.HttpClient` but connects only through `SsrfGuard`'s resolver, closing the DNS-rebinding window between the URL check and the connect on ~30 call sites (MCP OAuth and registry, A2A, Google/Meta/Slack/Teams/Discord/X/Telegram channel calls, skill registry, web search, x402, embeddings, image/video generation, the LLM blocking and streaming paths, GCP KMS, Twilio). The 14 deliberately-raw remainders target operator-configured private hosts (the sidecar, SearXNG, Langfuse, internal probes) the guard is meant to refuse.
- **A model can no longer repeat the same lookup inside one reply.** An identical `web_search`, `fetch_web_page`, knowledge or guide call (same arguments up to key order) later in the same reply is answered with "use the earlier result" instead of running; repeating again after that ends the loop with a short fixed reply. Only idempotent retrieval tools are guarded by default (`app.chat.tools.repeat-guard.tools`); the 4B local model used to re-issue the same search before answering.
- **Streaming chat replays a request once when Ollama rejects the model's tool call as malformed XML** (`HTTP 500 ... XML syntax error ... element <function> closed by </parameter>`). The blocking path already retried 5xx; the streaming path did not. Partial: in the reproduced multi-step browsing case the replay failed the same way, so the cause (what the model writes, or what Ollama does with it) is still open.
- **Personal: embeddings follow the Ollama you registered.** `app.embeddings.provider=auto` decided at start-up from environment properties only, so an Ollama chosen in the console's local-model wizard (with the local-AI bootstrap off) was invisible: embeddings fell to the sidecar, collections already embedded by Ollama silently lost vector search, and without the `rag` profile embeddings failed. `auto` now also uses an Ollama registered at run time (a platform-pool row pointing at the managed model server, checked per call and cached 30 s); a cloud key and an Ollama named in the environment still win, and the sidecar is the fallback.
- **The agent's browser could not start in the container at all.** Playwright finds its bundled driver with the thread's context class loader, which on the browser's worker thread cannot see the driver jar nested in the Spring Boot fat jar (`Failed to create driver`); core now hands it its own loader. The personal stack also mounts `/tmp` `noexec`, so the add-on overlay points Playwright at the image's Node (`PLAYWRIGHT_NODEJS_PATH`). Start-up errors now carry the root cause and a log line instead of a bare "Failed to create driver".
- **Personal: a browsing request reaches the whole browser toolset.** The personal profile raises the per-turn tool budget (24 tools, 6000 schema tokens; the always-kept tools used most of the shared 12/3000), the selector keeps the built-in `browser_*` tools together once one is picked, and small-model mode keeps up to four of them (navigate, read, click, type) for a request about driving a page.
- **Personal: web, channel and browser tools reach the model.** The relevance selector no longer leaves a request that names a tool with no scored slots when the always-kept set already fills the cap (about 15 names against 12): a matching tool now gets a small reserved floor. Small-model mode also keeps the best tool for each intent a request voices (search the web and list files), and knows routines (`schedule_task`) and machine questions (`local_shell`) without a shared word.
- **Personal: a free local model is no longer billed.** The call log re-priced every call from the shared catalog, so a zero-cost local pool row was booked at the unknown-model default rate into `llm_call_log`, the monthly spend counter and the hosted-spend cap; it now stores the advisor's own estimate.
- **Guardrails: a stalled thread no longer blocks harmless tool output.** A linear (RE2/J) rule that missed its 250 ms wall-clock deadline (a laptop under load, a paused VM) is retried once with a fresh deadline before failing closed; the step cap is unchanged.
- **Personal: continuation passes and background calls keep the tenant.** The tool-result continuation in the fast stream turn runs inside the captured tenant scope, so `llm_call_log` and `rl_episode` rows are written instead of failing with a missing-schema error.
- **Personal: WhatsApp QR says what is wrong.** With no bridge configured the receiver stops instead of polling forever and the channel shows "WhatsApp bridge not configured"; the overlay passes `APP_WHATSAPPQR_BRIDGE_URL` and `APP_WHATSAPPQR_BRIDGE_SECRET` to core.
- **Personal: share pages and A2A discovery reach core inside Docker.** The share-page layouts and the `/.well-known/agent-card.json` proxy fell back to `http://localhost:8080`, which inside the web container is the web container itself; both now prefer `CORE_INTERNAL_URL` (compose already sets it to `http://core:8080`).
- **Setup preflight no longer fails on ports the running install owns.** Ports published by this stack's own containers are reported as in use *by VegaDūta* instead of blocking a re-run, matching what `doctor` already does.
- **Setup: the wizard finds a Docker CLI it did not put on PATH.** A Finder-launched app gets a minimal PATH and Docker Desktop links its CLI under `~/.docker/bin` first (the `/usr/local/bin` symlink appears only after the app's privileged first run), so a fresh install with a running engine still reported "docker command not found". The wizard now appends `~/.docker/bin` to its PATH for itself and every child process.
- **Setup: a failed `brew install docker-desktop` says how to recover.** Stale root-owned files from an older Docker install make brew stop on a sudo prompt it cannot answer; the wizard now prints the cleanup command and the manual install link instead of a bare failure.
- **Personal: host RAM and accelerator are persisted.** `HOST_RAM_GB`/`HOST_ACCELERATOR` were only exported for the `personal` run that computed them; a restart or doctor from another shell silently reported `0`. Both are now written to `.env` (and documented in `.env.example`).
- **Personal: the /connect page is honest about webhook channels.** Slack and SMS cards carry a "Needs a public address" badge (they cannot receive on localhost), and the WhatsApp card goes to the QR-pairing flow that works on a laptop instead of the Meta API page.
- **Personal: changing `WEB_HOST_PORT` or `CORE_HOST_PORT` works.** `scripts/vegaduta personal` keeps `PUBLIC_APP_URL` and `PUBLIC_API_URL` in step with the ports when they are the generated `http://localhost:<port>` form (a `--domain` install is untouched), and the compose defaults derive from the port variables.
- **Personal console.** The Agents page shows real labels instead of raw message keys, `/research` is hidden from the rail unless research runs are on, workflow nodes the install cannot run (`wait`, `voice_menu`, `bulk_email`, `crm_lead`, `device_control`) are no longer offered in the palette, and a refused refresh no longer clears the session cookie (two tabs refreshing together signed the person out).
- **Personal: smaller papercuts.** Valkey keeps 128 MB (a rate-limit counter evicted under pressure fails open), the localhost public-URL notice is INFO on a personal install, the shell tool tells the model it is on a Mac (BSD flags), `schedule_task` says to omit the delivery fields unless named, and the Docker Desktop cask is `docker-desktop`.
- **Nothing runs after an action is parked for approval.** When a tool call was held for the user's approval, the model was told so and could keep going with other tools (often ones that depended on the held one) and finish the task before the user decided. The turn is now paused at the first held call: every other tool call in that turn is refused, and the model is told to stop and say what is waiting. The Assistant's prompt and the "carry on" context say the same. Separately, `keyValue` nodes in a `json_ui` block were being rejected as unsupported (the node type was lower-cased before the lookup).
- **Local thinking models answer in seconds, not 30-plus.** The install's own Ollama now gets `reasoning_effort: none` (`app.llm.ollama.reasoning-effort`, default `none`; `low`/`medium`/`high` or blank to opt back in). Measured on `qwen3.5:4b`: a one-line question spent 40+ s and 600 tokens thinking before it answered, against about 5 s with reasoning off.
- **The Assistant can read the knowledge base, and its agent picker changes agent.** An Assistant whose knowledge base was left off (the switch at creation is best-effort and can fail quietly) said it could not read the person's documents; it is now switched back on when the Assistant loads, and the small-model tool choice offers `search_knowledge_base` for requests about uploaded documents. The picker could never leave the first agent: the `?agent=` link seeded the choice but also outvoted every later pick, and each pick was written back to that same URL. The link now only seeds or re-seeds the selection.
- **Attaching a file or photo in the Assistant works on a personal install again.** The projects folder is shared by core (uid 999, which saves chat uploads) and the workspace runner (uid 1000); when the runner created the volume first, core was refused with `AccessDeniedException: /workspace/Chat uploads`. A one-shot `workspace-perms` service in `personal.yml` now opens the named volume before core starts (a host folder chosen with `VEGADUTA_PROJECTS_DIR` keeps its own permissions).
- **A small local model is offered the tool that fits the request.** Small-model mode keeps six tools, chosen by word overlap, which missed most real requests ("what is the weather in Goa" shares no word with `web_search`), so the model was offered unrelated tools and then asked for one it did not have. An intent table now matches web-search wording, URLs, mail/calendar/Drive words, file and project words, memory words and document words to the tools that serve them.
- **A slow careful turn no longer ends as "every model failed".** A CAREFUL/RIGOROUS/PLANNED turn that hits `app.llm.http.buffered-turn-timeout` is now answered at FAST depth without tools (metric `chat.degraded.depth_timeout`, a `guardrail` step event in the trace) instead of discarding four minutes of work and reporting the pool exhausted. A hosted-pool row whose stored parameter count disagrees with its model tag by more than half now trusts the tag, so a row repointed from a 9B to a 4B model enters small-model mode (FAST, six tools, compact directives) instead of keeping the larger model's settings. The local-model warm-up compares the context Ollama actually loaded with `app.llm.ollama.num-ctx` and logs the `OLLAMA_CONTEXT_LENGTH` fix when the runner ignored the request (the MLX runner does).
- **Thinking models on the install's own Ollama now stream their reasoning.** The platform-pool row the local-LLM bootstrap (or `/use`) creates is served by the hosted-pool client, which did not apply the Ollama reasoning-field alias or the `num_ctx` override that a tenant OLLAMA provider row gets; so `thinking` step events never appeared on a personal install, and long tool turns could hit the 2k default context. Rows pointing at `app.local-models.ollama-base-url` (or marked OLLAMA) now get both.
- **Installers: personal install works from `curl | sh` on Debian/Ubuntu and from the Windows Setup app.** `install.sh personal` used a bash-only substitution that fails under dash; `vegaduta.ps1 personal` now understands the `workspace` and `rag` profiles and prints the first-run link, and the wizard passes PowerShell-style flags (`-Profile`, `-Lite`/`-Full`) on Windows instead of letting `--profile` leak into `docker compose`. ### Security

  lacked `@Valid` are now validated; payment checkout and the developer API
  no longer echo raw exception text; private-address detection uses real
  address ranges (172.16/12, not all of 172/8); the remote MCP pre-probe goes

  reprice what the tenant sells. The authorization coverage test now also

  config read-only and runs with `no-new-privileges`, a memory limit and a
  healthcheck.
- code-intel, app-builder and rl-trainer accept `KEYCLOAK_ADDITIONAL_ISSUERS`
  (also `<SERVICE>_KEYCLOAK_ADDITIONAL_ISSUERS`) like core does, so a domain
  migration no longer answers 401 from those services while core accepts the
  same token. Their `*_KEYCLOAK_ISSUER` no longer defaults to localhost: with
  `*_AUTH_MODE=keycloak` and no issuer set, token requests answer 503.
- The CI job that boots core mints a throwaway `APP_ENCRYPTION_KEY` per run
  instead of carrying a literal key in the workflow.
- Web console: the plain-HTTP-to-HTTPS redirect now targets the request's own
  URL instead of the `Host` header, which anyone reaching the origin directly
  could set to another site (open redirect). `/api/eval/*` is gated to
  development like `/eval`. The chat stream parser caps what it buffers for
  one line or one event (4 MB) instead of growing without bound. The legal
  page escapes the configured contact address before rendering it as markup.
- Platform-admin console: the Content-Security-Policy no longer allows
  connections to any `wss:` host (it opens no WebSockets).
- Both consoles: a production build with `NEXT_PUBLIC_API_BASE_URL` or
  `NEXT_PUBLIC_KEYCLOAK_URL` unset no longer falls back to `localhost`
  silently (the fallback was copied into ~20 files); `publicApiBase()` /
  `publicKeycloakUrl()` keep the dev default outside production and report
  a missing value once.
- Granting or revoking an agent payment mandate requires the billing
  permission (tenant-admin by default). Any signed-in member could do it.
- Closed authorization gaps any signed-in member could use: answering
  another user's pending workflow form (now needs run access to that
  workflow), commanding or revoking any paired phone, publishing or taking
  down any studio app, spending LLM budget on or accepting suggestions for
  any agent's improvements, and re-routing email, Telegram and voice
  channels or unpairing live conversations.
- Users whose only role is end-customer can no longer make console changes:
  they can chat with agents (text and voice) and manage their own account and
  notifications, nothing else. A user with any other role is unaffected.
- More console writes now require the matching permission instead of any
  signed-in member: creating agents and workflows (agent permission; a
  delegated user may still create agents and edit its own), duplicating agents
  and importing templates, script tools (tools permission), ad-hoc channel
  sends and device pairing (channels permission). Skills, human handoff and
  moderation decisions already checked these in the handler; the security
  configuration now records them too.
- Changing an agent's content guardrails needs the guardrails permission;
  sharing or submitting a community template needs the templates permission;
  cloning or deleting ElevenLabs voices needs the channels permission, like
  the ElevenLabs key; running the decision playground needs the integrations
  permission. The console shows these controls as read-only, hidden or
  disabled, with the reason, for members without the permission.
- Ownership checks inside handlers: stopping a chat turn works only on the
  caller's own session (and now also stops turns routed into an A/B
  experiment); cancelling a job needs to be its requester or an editor of the
  agent; reading or deleting what an agent remembers about someone else needs
  editor access; a vision session needs chat access to start and can only be
  ended by whoever started it; a collaborator agent can only be added by
  someone who can run it; a chat session's prompts and costs are visible to
  the person who had the session and to the agent's editors (anyone who knew
  the session id could read them); pointing an agent at code-intel repos or
  giving it a code workspace needs the tenant-admin or agent-builder role, like
  the rest of code intelligence.
- In-app call recording can only be started or stopped by the person the call
  was issued to. Anyone who knew a room name could record that call.
- Rating an agent's reply (thumbs, rating, edit) needs chat access to the
  agent and only works on your own turns; feedback can no longer skew another
  user's reward or plant answers in the preference export. Importing a chat
  turn into an eval dataset copies the recorded turn only when it was yours.
- Approving or rejecting a workflow step's approval needs run access to that
  workflow (any member except the requester could decide it).
- Request body caps and password length limits; rate limits on previously
  unthrottled public endpoints (limiters never fail open).
- The page Content-Security-Policy reports violations to `/api/csp-report`.
- Skill supply-chain scanning, content-hash pinning and a review gate;
  `http_request` safe mode (https only, allow-lists, named credentials).
- Binary GET responses are no longer decoded as text, which corrupted
  downloaded generated documents.
- New configuration endpoints need the matching tenant permission: agent
  hooks (`MANAGE_GUARDRAILS` or tenant admin), tool argument policies
  (`MANAGE_GUARDRAILS`), MCP tool exposure (`MANAGE_INTEGRATIONS`), agent
  import, judge-calibration sets and trajectory expectations
  (`MANAGE_AGENTS`), workflow import (`MANAGE_WORKFLOWS_ADMIN`). Chat
  edit / regenerate / branch switching only works on the caller's own session.

### Performance

- **Tenant sweep cost measured, idle-skip decision recorded** ([Tenant sweep cost](docs/architecture/TENANT-SWEEP-COST.md)). One jobs pod with one idle tenant makes about 1.0 tenant-scoped database calls per second, which grows linearly with tenants (extrapolated, not run); idle-skip covers about 22% of them and adds up to 30 s to agent-job and webhook pick-up, so it stays off by default. New counter `vegaduta_tenant_sweep_tenants_total{job,outcome}` and a test that proves the staleness bound of idle-skip at every position of its back-off. The on/off comparison and a many-tenant run were not done.
- **Post-merge benchmark numbers** for the whole turn (two replicas, 1/8/32 users, caches on and off) in `docs/architecture/HOT-PATH-PERFORMANCE.md` section 4b, with the raw results next to the harness.
- **Hot-path performance, third step: each per-turn fact is looked up once.** A chat turn read the tenant's plan up to a dozen times (preflight, the inbound guardrail check, the gateway's budget and rate-limit checks for every client it built, and one per RL dimension on a Playground turn), evaluated the tenant's feature flags three times (version pin, effective-agent overlay, experiment variants), resolved the MCP tools a second time just to learn whether any are offered, and embedded the user message twice (agent memory, then tenant-shared memory). The plan and the flags are now resolved once in preflight and handed down, the tool resolution returns its MCP answer with the tool list, and the two memory recalls share one embedding (`QueryEmbedding`). Defaults are unchanged and every path that does not hold the value still looks it up as before. `ChatTurnLookupCountTest` locks the per-turn counts on a real `chat()` turn; `HotPathQueryBudgetIT` measures the plan and flag lookups on a real Postgres. `app.chat.hotpath.plan-cache-ttl` stays `0s`: with the plan passed down it could save at most one lookup per turn. The outbound guardrail check and the delegated-call, specialist and workflow clients still read the plan (listed in `docs/architecture/HOT-PATH-PERFORMANCE.md`). Milliseconds were not measured.
- **Per-turn latency harness and first measured numbers.** `tests/load/scripts/turn-overhead.js`, a mock Ollama-compatible model server (`tests/load/mock-llm`) and `tests/load/kind/bench.sh` measure platform overhead per chat turn in milliseconds on a local kind stage, with no model cost. First results (one laptop, mock model): about 50 to 60 ms of platform overhead per idle turn; the hot-path caches save about 20 ms per turn at idle and about 40% throughput at 8 users. Method, table and limits in `docs/architecture/HOT-PATH-PERFORMANCE.md`.
- **Hot-path performance, third step: tool resolution reads nothing when warm.** The last eight transactions of tool resolution (Google connection status, the hosted image pool check, skills metadata and settings, user scripts, custom code tools, OpenAPI tools) now go through the same `HotpathLookups` cache as immutable snapshot records (never a detached JPA entity), evicted on a write to the underlying entity on the same pod (new `@PlatformConfigEntity` marker for the platform-wide hosted pool rows). The tool callbacks of custom code and OpenAPI tools re-read their row when the model calls them, so an edit or a disable applies to the next call and no source code or secret sits in the cache. Warm tool resolution for one turn of a default agent: 8 to 0 connection checkouts, 11 to 0 statements. `HotPathQueryBudgetIT` now also counts a whole turn from the pre-flight checks to the first token against a mock model (warm: 15 connections, 14 statements; cold: 44 and 46) and runs with `app.chat.hotpath.config-lookup-ttl=0s` to prove the old behaviour. Same TTL setting as before (`0s` = off).
- **Hot-path performance, second step.** The "is this configured" checks the tool resolvers make on every turn (any MCP server enabled, ElevenLabs, Sarvam and E2B credentials, image and video providers, payment mandate, specialist tags, platform tool credentials) now go through a small tenant-keyed read-through cache (`HotpathLookups`), evicted on a write to the underlying entity on the same pod. `app.chat.hotpath.config-lookup-ttl` (default `3s`, max `30s`, `0s` = off) bounds staleness on other replicas. Warm tool resolution for one turn of a default agent: 23 to 8 connection checkouts, 26 to 11 statements, measured by `HotPathQueryBudgetIT` (now with a cold and a warm number). The scheduling-role skip no longer logs a line for every bean when a pool skips a broad package; it logs only beans with scheduled methods.
- **Hot-path performance** ([Hot-path performance](docs/architecture/HOT-PATH-PERFORMANCE.md)). A chat turn's 16 read-only agent lookups (tool allowlist, autonomy tier, capability flags, knowledge scope, run budget) were each their own database transaction, and every transaction costs three round trips because of the per-tenant `SET search_path`. They now read an immutable per-pod snapshot, evicted on every agent write on that pod. Measured on a real Postgres for the tool-resolution step of one turn of a default agent: 52 to 23 connection checkouts, 55 to 26 statements. `app.chat.hotpath.agent-projection-ttl` (default `3s`, max `30s`; `0s` restores the old behaviour) bounds how stale another replica can be. Authorization and edits never read the cache. New `HotPathQueryBudgetIT` records the budget so a new per-turn query has to be justified.
- Opt-in `service.trafficDistribution` (`PreferClose`) on the Helm Services and `examples/values-low-latency.yaml`, to keep pod-to-pod calls in the caller's zone (Kubernetes 1.31 or later). Not measured on a multi-zone cluster.
