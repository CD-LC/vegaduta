# Deploying VegaDūta

Everything needed to run the platform yourself. Pick a tier:

| Tier | What you get | Containers | RAM (Docker) | Disk | How |
|---|---|---|---|---|---|
| **Lite** | Agents, chat, knowledge (optional RAG sidecar), graph memory, one-machine use | 5 (+1 with `rag`) | 6 GB (fits an 8 GB laptop) | 15 GB | `scripts/vegaduta up --lite` |
| **Full** | Everything in Lite + platform-admin console, S3 object storage, PgBouncer, optional workflows/Temporal, observability, tracing, voice, code-intel, app builder, sandboxes | 10 core, up to 36 with all profiles | 12 GB core set, 24 GB+ with all profiles | 40 GB | `scripts/vegaduta up --full [--profile …]` |
| **Kubernetes** | Production HA | — | — | — | see [`deploy/helm`](helm/README.md) |

Windows: use `.\scripts\vegaduta.ps1` with the same commands (`-Lite`, `-Full`, `-Profile x,y`, `-Build`, `-Domain`).

## Quick start

```sh
# from a checkout (or: curl -fsSL https://raw.githubusercontent.com/CD-LC/vegaduta/main/install.sh | sh)
scripts/vegaduta up --lite
```

`up` generates `deploy/compose/.env` with random secrets (never overwriting existing values), runs `doctor`, starts the stack, waits until every service is **healthy**, applies the Keycloak realm fixes, and prints the URLs:

| | Lite / local full |
|---|---|
| Console | http://localhost:3000 |
| API | http://localhost:8080 |
| Keycloak | http://localhost:8180 (admin console at `/admin`) |
| Platform admin (full) | http://localhost:3001 |

**First login:** open the console → **Sign up** (the first account creates your organisation) → `scripts/vegaduta make-admin you@example.com` to become platform operator → add an LLM provider key in the console.

Until release images are published to `ghcr.io/cd-lc`, add `--build` to build from source (needs ~15 GB free and 10–30 min the first time):

```sh
scripts/vegaduta up --lite --build
# equivalent raw compose:
docker compose -f deploy/compose/lite.yml -f deploy/compose/lite.build.yml --env-file deploy/compose/.env up -d --build --wait
```

## Full-stack profiles

The bare `up --full` core set: `postgres`, `pgbouncer`, `valkey`, `seaweedfs`, `keycloak`, `keycloak-db`, `sidecar`, `core`, `web` (the platform-admin console is part of it under /platform-admin).

| Profile | Adds | Also set (the CLI does it for you) |
|---|---|---|
| `events` | redpanda (Kafka API, BSL-1.1 — see NOTICE) | `CORE_PROFILES_EXTRA=,workflow` |
| `temporal` | temporal, temporal-postgresql, temporal-ui, core-worker (implies `events`) | `CORE_PROFILES_EXTRA=,workflow,temporal`, `WORKFLOW_EXECUTION_ENGINE=temporal` |
| `jobs` | core-jobs (implies `temporal`) | `CORE_SHAPE_PROFILE=,shape-api` so the API leaves the sweeps and pollers to core-jobs |
| `observability` | prometheus, grafana, loki, promtail, alertmanager, valkey-exporter | — |
| `tracing` | langfuse web+worker, its postgres, clickhouse, valkey, S3 | `TRACING_SAMPLING_PROBABILITY=0.1` to start sending |
| `voice` | livekit, voice-agent | `LIVEKIT_BIND_ADDR=0.0.0.0` + UDP 50000-50100 for remote callers (`LIVEKIT_RTC_PORT_RANGE_START` / `_END` move the range) |
| `rl` | rl-trainer | `ANTHROPIC_API_KEY` |
| `code-intel` | code-intel + its private docker-in-docker executor (privileged) | `CODE_INTEL_ENABLED=true` |
| `builder` | app-builder (implies `code-intel`) | — |
| `sandbox` | tool-sandbox, mcp-stdio-runner | `TOOL_SANDBOX_ENABLED=true`, `MCP_STDIO_SIDECAR_ENABLED=true`, `CORE_MCP_PROFILE=,mcp` |
| `tools` | mcp-stdio-runner (stdio MCP servers, incl. the built-in filesystem/memory/sequential-thinking) | `MCP_STDIO_SIDECAR_ENABLED=true`, `CORE_MCP_PROFILE=,mcp` |
| `browser` | mcp-stdio-runner from the `mcp-stdio-runner-browser` image (adds the puppeteer / playwright-vision built-ins) | as `tools`, plus `MCP_STDIO_RUNNER_VARIANT=-browser`, `MCP_STDIO_RUNNER_WITH_BROWSERS=true` (build overlay), `MCP_STDIO_RUNNER_MEM_LIMIT=2g` |

```sh
scripts/vegaduta up --full --profile temporal --profile observability
# raw compose (set the "Also set" variables in .env yourself):
docker compose -f deploy/compose/docker-compose.yml --env-file deploy/compose/.env \
  --profile temporal --profile observability up -d --wait
```

Resource limits are set on every service (`deploy.resources.limits`); tune with the `*_MEM_LIMIT` variables in `.env`.

### Essential vs plug-and-play

The `core` image is slim: no Node/npm, uv or browsers (`core/Dockerfile`
`MCP_TOOLCHAIN=none`). Stdio MCP servers, the `mcp` profile's built-ins
included, run in `mcp-stdio-runner` (profiles `tools` / `browser`). Without the
runner, core runs without the `mcp` profile; if you force `mcp` on the slim
image core refuses to start and says why. Hosts that cannot run the runner can
use `CORE_IMAGE_VARIANT=-full` + `CORE_MCP_PROFILE=,mcp` (the ~6 GB `core-full`
image; `CORE_MCP_TOOLCHAIN=full` with the build overlay).

| Service | Class | Turn on with |
|---|---|---|
| core, web, postgres, valkey, keycloak | essential | always |
| core-jobs / core-worker | scale shape | `--profile jobs` / `--profile temporal` |
| migrate | scale shape | Helm only (Compose: the API migrates on boot) |
| mcp-stdio-runner | plug-and-play | `--profile tools` |
| mcp-stdio-runner-browser | plug-and-play | `--profile browser` |
| sidecar | plug-and-play | on in full; `--profile rag` in lite |
| tool-sandbox | plug-and-play | `--profile sandbox` |
| code-intel / app-builder | plug-and-play | `--profile code-intel` / `--profile builder` |
| voice-agent / rl-trainer | plug-and-play | `--profile voice` / `--profile rl` |

What each one enables and its core flag: [docs/configuration.md](../docs/configuration.md#essential-vs-plug-and-play-services).

## Running on a server with a domain

1. DNS: `app.`, `admin.`, `api.`, `auth.` (plus `codeintel.`, `builder.`, `livekit.` if used) → your server. In the default Let's Encrypt mode the bare domain and `www.` are also served (they redirect to `app.`), so Caddy requests certificates for them too: point them at this server as well, or ACME validation for those two names fails and retries on every start. Behind a tunnel or TLS proxy (`CADDY_AUTO_HTTPS=off`) no certificates are requested and this does not apply.
2. `scripts/vegaduta up --full --domain example.com` (writes `BASE_DOMAIN`, `PUBLIC_*` into `.env` and adds `docker-compose.domain.yml`).
3. Ports 80/443 open; Caddy obtains certificates. Behind an existing TLS proxy or tunnel, set `CADDY_AUTO_HTTPS=off` **and** `CADDY_SITE_SCHEME=http://` and forward to port 80 ([walkthrough](../docs/operations/tunnel-hosting.md)). In that mode also set `PUBLIC_BIND_ADDR=127.0.0.1`: it defaults to `0.0.0.0`, which would leave plain-HTTP port 80 (Keycloak logins included) reachable directly, bypassing the tunnel's access controls.

**Issuer consistency.** Keycloak stamps tokens with `PUBLIC_AUTH_URL/realms/<realm>` (`KC_HOSTNAME`); core, code-intel, app-builder and rl-trainer validate that exact issuer and fetch keys internally from `http://keycloak:8080`. Changing the domain later changes the issuer: add the old one to `KEYCLOAK_ADDITIONAL_ISSUERS` during the switch. Redirect URIs/web origins are written into the realm at first import from `PUBLIC_APP_URL`/`PUBLIC_ADMIN_URL`, and every `scripts/vegaduta up` (the realm reconcile) then **adds** the derived entry to the `agentic-ai-web` and `agentic-ai-platform-admin` clients if it is missing. The reconcile merges: URIs and origins you added by hand are kept, and entries for a previous domain are not removed, so delete those in the Keycloak admin console (reachable only on `127.0.0.1:8180` in domain mode — `ssh -L 8180:127.0.0.1:8180 server`).

Never point a `PUBLIC_*` URL at `localhost` on a server — browsers of other users would call their own machine. `scripts/vegaduta doctor` checks this.

## Object storage

Full stack ships **SeaweedFS** (Apache-2.0) as an S3 gateway; core creates its bucket on boot. To use AWS S3, R2, Ceph, Garage or any S3 API, set `STORAGE_ENDPOINT`, `STORAGE_ACCESS_KEY`, `STORAGE_SECRET_KEY`, `STORAGE_REGION`, `STORAGE_PATH_STYLE_ACCESS` and stop `seaweedfs`. Lite stores files on the `core-storage` volume.

## Operations

```sh
scripts/vegaduta status              # service state + health
scripts/vegaduta logs core           # follow one service (omit for all)
scripts/vegaduta doctor              # docker/compose versions, RAM, disk, ports, secrets, URLs
scripts/vegaduta down                # stop (data kept); --volumes deletes data after confirmation
scripts/vegaduta compose <args>      # raw docker compose with the right files/profiles
```

### Backup and restore

Back up **`deploy/compose/.env` together with the data** — `APP_ENCRYPTION_KEY` decrypts every stored provider key and channel secret; a database without it is not restorable.

```sh
scripts/vegaduta backup                       # -> deploy/compose/backups/<timestamp>/ (mode 700/600)
scripts/vegaduta restore deploy/compose/backups/<timestamp>   # asks first; stops writers, pg_restore, up
```

A backup holds `app-db.dump` (and `keycloak-db.dump` on full; `pg_dump -Fc`), dumps of the profiled auxiliary databases when they run (`temporal-postgresql.dump`, `langfuse-postgres.dump`), `files.tar.gz` (the `seaweedfs-data` or `core-storage` volume; skipped for an external S3 bucket, back that up yourself), `env` (a copy of `.env`) and a `MANIFEST`. Move `env` to a separate secret store before the backup leaves the machine: it holds `APP_ENCRYPTION_KEY`, and a dump stored next to its key is a dump stored in the clear (see [docs/operations/key-rotation.md](../docs/operations/key-rotation.md)). Lite keeps Keycloak users in the `keycloak-data` volume (dev-file store): archive it with the stack stopped, e.g. `docker run --rm -v vegaduta-lite_keycloak-data:/d -v "$PWD":/b alpine tar czf /b/keycloak-data.tgz -C /d .`. `restore` does not unpack `files.tar.gz`; extract it into the volume with the stack stopped. Test a restore on a spare machine before you need it.

### Upgrade

```sh
scripts/vegaduta upgrade --version 1.2.0   # backup, verify + fetch release files, pull, recreate, wait for health
```

`upgrade` takes a `backup` first and aborts when that fails (`--no-backup` skips it). On an install from a release tarball it downloads the target release's compose files, verifies them against the release `SHA256SUMS` (and its Sigstore bundle when `cosign` is installed) and continues with them; in a git checkout, `git checkout v1.2.0` first. Database migrations (Flyway) run when core starts and are forward-only: when the new version does not become healthy, `upgrade` prints the rollback (`upgrade --version <previous> --no-backup`, then `restore <backup>`). It never regenerates existing secrets but adds new ones. Read the release notes first.

**Auxiliary Postgres 16/17 → 18.** `keycloak-db`, `temporal-postgresql` and `langfuse-postgres` run the stock `postgres` image, which moved to PostgreSQL 18. From 18 the official image keeps the cluster at `/var/lib/postgresql/<major>/docker` inside the mounted volume and refuses to start while it finds a pre-18 cluster (or anything mounted at the old `/var/lib/postgresql/data` path), so an **existing volume does not carry over** — that container exits with the upstream "PostgreSQL data in /var/lib/postgresql" error until the data is migrated. The pre-upgrade `backup` already dumps all three databases. To migrate one of them afterwards, recreate its volume and replay the dump (repeat per service; `vegaduta` is the default compose project name — check `docker volume ls` if `COMPOSE_PROJECT_NAME` was set):

```sh
scripts/vegaduta compose rm -fs keycloak-db
docker volume rm vegaduta_keycloak-db-data          # drops the pg16 cluster; the dump is in the backup
scripts/vegaduta compose up -d --wait keycloak-db   # initdb a fresh pg18 cluster
scripts/vegaduta compose exec -T keycloak-db sh -c \
  'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists --no-owner --exit-on-error' \
  < deploy/compose/backups/<timestamp>/keycloak-db.dump
```

For `temporal-postgresql` (`temporal-db-data`, `temporal-postgresql.dump`) and `langfuse-postgres` (`langfuse-postgres-data`, `langfuse-postgres.dump`) use `"${POSTGRES_DB:-$POSTGRES_USER}"` as the `-d` argument, and only bother when the profile ran and the data matters: Temporal's `auto-setup` recreates an empty schema, Keycloak re-imports the realm on boot, and Langfuse keeps traces in ClickHouse/S3 — skipping the migration costs Keycloak users created after install, workflow history and Langfuse accounts, nothing else. `pg_upgrade` is not available here (the stock images ship one major each); staying on the previous release's compose pin is a valid alternative until the migration can be scheduled.

### Lite → full

Different projects and stores: Postgres data can be carried over with `pg_dumpall`/restore; Keycloak users move via a realm export (`kc.sh export`) from the lite container and import into the full one; files move from the `core-storage` volume into the S3 bucket.

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| Every API call returns 401 after login | Token issuer ≠ what core expects. `PUBLIC_AUTH_URL` must be exactly the URL the browser uses for Keycloak; add other issuers to `KEYCLOAK_ADDITIONAL_ISSUERS`. |
| Login redirects to `localhost` on a server | `PUBLIC_*` still localhost — `scripts/vegaduta secrets --domain example.com`, then `up`. For images built with `--build`, rebuild web so the fallback URLs change too. |
| "Invalid redirect URI" on login | Realm clients were imported with other URLs; fix `agentic-ai-web` redirect URIs/web origins in the Keycloak admin console. |
| Signup succeeds but the console is empty / 500s | `tenant_id` attribute dropped — re-run the realm reconcile: `scripts/vegaduta up` (or `deploy/keycloak/reconcile-keycloak.sh`). |
| Stored provider keys "cannot be decrypted" | `APP_ENCRYPTION_KEY` changed. Restore the original value; there is no other recovery. |
| `core` unhealthy on first start | First boot runs all migrations; allow ~3 min. Then `scripts/vegaduta logs core`. Check RAM with `doctor`. |
| `up` fails: `port is already allocated` | Another service holds the port; change `*_HOST_PORT` / `BIND_ADDR` in `.env`. |
| Workflows don't run | Enable `--profile events` (or `temporal`); the `workflow` Spring profile needs Kafka. |
| LiveKit `address already in use` on a UDP port | Another process on the host (for example `adb`) holds a port in 50000-50100; set `LIVEKIT_RTC_PORT_RANGE_START` / `_END` in `.env` to a free range |
| Voice connects but no audio | WebRTC media needs UDP 50000-50100 reachable and `LIVEKIT_BIND_ADDR=0.0.0.0`; configure TURN in `livekit/livekit.yaml` for strict NATs. |
