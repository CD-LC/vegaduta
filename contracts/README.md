# contracts/ — inbound/outbound wire-format contracts + fixture corpus

> **Consumer-driven contracts** between core's REST API and its clients live in
> `contracts/consumers/<consumer>/*.contract.json` (the web console in `consumers/web/`, generated by
> `web/scripts/api-contract.mjs`). Core's `ConsumerContractVerificationTest` checks every interaction against
> the OpenAPI document generated from the controllers. Format and rules:
> [ADR-0025](../docs/architecture/ADR-0025-consumer-driven-contracts.md). The rest of this file is about the
> webhook/WebSocket wire formats below.

B9-PR4 (`VegaDuta-PR-Prompts-B9-A1.md`). Two things live here:

1. **JSON Schemas** describing every wire shape a webhook/WebSocket handler actually
   parses or emits — sourced by reading the handler/DTO itself, not by guessing from a
   vendor's general docs. Each schema's header comment says exactly which source file
   it was derived from and when, so a future change to that file is the signal to
   re-derive the schema, not the other way around.
2. **Fixtures** — real (or deliberately-malformed) example payloads that validate (or
   are asserted to fail) against those schemas, and that the corresponding contract
   test replays against the real handler code.

## Layout

```
contracts/

      schemas/*.schema.json

      schemas/*.schema.json      # add the actual HTTP endpoint that calls this parser -
      fixtures/*.json            # this PR ships fixtures+schemas ONLY, contracts-first)
    telegram/                    # reserved for D9 (omnichannel channel expansion) -
    slack/                       # empty on purpose, do not fill in from this PR
  outbound/
    audit-event.schema.json         # core/audit's AuditLogEntryResponse
    approval-callback.schema.json   # core/approval's ApprovalRequestResponse
```

## Twilio Conversation Relay (inbound)

Source: `core/omnichannel/src/main/java/com/agenticai/core/omnichannel/twilio/VoiceRelayWebSocketHandler.java`
(read directly, not Twilio's general docs — schemas cover exactly the fields
`handleTextMessage`'s `switch` and each `handleXxx` method actually read via
Jackson's `JsonNode.path(...)`, nothing more). Twilio's real Conversation Relay
messages carry additional fields (e.g. `prompt`'s `lang`, `confidence`); those aren't
schema'd here because the handler never reads them — see each schema's own comment.

Five message `type`s are handled: `setup`, `prompt`, `interrupt`, `dtmf`, `error`. Any
other `type` value is silently ignored (`default -> log.debug(...)`) — there is no
"unknown message type" failure mode to test for on the happy path; the malformed-JSON
fixture (`fixtures/malformed-not-json.txt`) exercises the actual failure mode instead
(`MAPPER.readTree` throwing `IOException`, caught and logged, connection stays open).

**`interrupt` has no schema** — the handler reads zero fields off it
(`case "interrupt" -> disposeActive(session)` takes no argument from `node` at all), so
there is nothing to validate beyond `{"type": "interrupt"}`. Its fixture exists purely
for the replay test (asserting the in-flight response gets disposed), not for schema
validation.

## Razorpay (inbound)

Source: `core/billing/src/main/java/com/agenticai/core/billing/gateway/RazorpayGatewayClient.java`
(`parseWebhookEvent` + `mapEventType` + `extractSubscriptionId`, read directly).

**Deviation from this PR's own task list, logged here on purpose (contracts-first means
schema what exists, not what the prompt assumed exists):** the original task list named
`subscription.activated, subscription.charged, payment.failed, subscription.halted,
subscription.cancelled, invoice.paid`. The actual `mapEventType` switch today only
recognizes ten `subscription.*` event names (`authenticated, activated, charged,
pending, halted, paused, resumed, cancelled, completed, updated`) — `payment.failed`
and `invoice.paid` are **not** in that switch and fall through to
`BillingEventType.UNKNOWN` today (not an error — `parseWebhookEvent` never throws on an
unrecognized `event` value, it just returns `UNKNOWN`). Schemas below cover the ten
real `subscription.*` types the parser actually maps, plus `payment.failed` as an
explicit **"recognized-envelope-shape, unknown-event-name" fixture** proving the parser
degrades gracefully (returns `UNKNOWN`, does not throw) rather than a type the parser
special-cases. When A1-PR2/PR3 actually add `payment.failed`/`invoice.paid` handling to
`mapEventType`, promote that fixture to its own schema at the same time — don't let the
fixture corpus silently drift from what the switch statement covers again.

Every fixture's envelope matches the shape `RazorpayGatewayClient`'s own comment
documents (`{"payload": {"subscription": {"entity": {"id": "sub_...", ...}}}}`) plus
the two headers `Utils.verifyWebhookSignature` / A1-PR2's future controller need:
`X-Razorpay-Event-Id`, `X-Razorpay-Signature` (HMAC-SHA256 hex digest of the raw body
against the webhook secret — Razorpay's own `Utils.verifyWebhookSignature(rawBody,
signatureHeader, webhookSecret)` static helper, already called from
`RazorpayGatewayClient#verifyWebhookSignature`). Each fixture file's `_meta.headers`
block records the exact header names A1-PR2 must read from the real HTTP request so
its `billing_webhook_events.gateway_event_id` column population matches
`X-Razorpay-Event-Id` (per this PR's own overlap-check note) — this is metadata for the
fixture corpus, not itself part of the JSON body Razorpay would ever send; the
generator script (`fixtures/generate-signatures.sh`) computes real HMAC signatures
against a fixture-only throwaway secret so a genuine `Utils.verifyWebhookSignature`
call, not just a schema check, can replay these once A1-PR2 exists.

## Outbound

`outbound/audit-event.schema.json` ← `core/audit/dto/AuditLogEntryResponse` (record
fields, `AuditOutcome` enum values inlined). `outbound/approval-callback.schema.json` ←
`core/approval/dto/ApprovalRequestResponse` (record fields, `ApprovalStatus` enum
values inlined, `payload` genuinely nullable per that field's own javadoc). Both
schemas were derived from the DTO `record`s Jackson actually serializes (`from(...)`
factory methods), not the JPA entities behind them.

## Running these locally

No Docker/full-stack needed — these are unit/schema-validation tests only (see
`.github/workflows/contract.yml`'s own header comment for why this job is deliberately
NOT part of `stack.yml`/`e2e.yml`). From `core/`:

```
mvn -pl omnichannel,billing,audit,approval -am test -Dgroups=contract
```

## Known gap, not fixed in this PR

No JSON Schema validator dependency (`networknt json-schema-validator` or similar)
exists anywhere in `core/`'s poms yet (checked `core/pom.xml` and `core/app/pom.xml` —
zero hits for `json-schema`/`networknt`/`everit`). The schema-validation JUnit test
drafted alongside these fixtures (delivered separately, not committed into `core/`
directly from this sandboxed thread — see `AGENT-COORDINATION-2026-07-18.md` §12 for
why) assumes that dependency gets added to whichever module hosts it. Whoever lands
these files for real needs to add it to that module's `pom.xml` first, or the
schema-validation test won't compile.
