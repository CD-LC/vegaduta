# Agent runtime defaults review

Decision document for the owner. The table below is the review as written on 2026-10-23; the owner then decided rows 1, 2, 3, 6, 10 and 12 (flipped) and row 11 (kept off), recorded at the end of each of those rows, and nothing else changed. See `docs/configuration.md` (Agent-runtime defaults set on 2026-10-23).
Checked 2026-10-23 against the uncommitted working tree (phases 1 and 2 present, phase 3 in progress), so a key named
here may move into a typed settings class; the property names are the contract.

## How to read this

- **Profiles.** `personal` is the shipped Spring profile (`application-personal.yml`): one person, one laptop, often a
  small local model, the user is also the approver. `team` and `enterprise` are not shipped profiles; they describe
  deployments. Team: one tenant, several trusted users, an admin exists (compose or lite stack). Enterprise: multi-tenant
  or regulated, Keycloak, Helm, several replicas, audit obligations.
- **Current default** is read from `core/app-config/src/main/resources/application.yml`, `application-personal.yml`
  and the code `@Value`/entity defaults, not from docs.
- **Test on the real path** means a test that drives a turn (or a job) through the real guard chain with the control
  switched on. `ApprovalTurnHarness` (agents-tools `e2e/`) is the only such rig, and its own javadoc lists what it does
  NOT exercise: tool classification, hooks, taint, argument policies, the effect journal, the circuit breaker, the
  buffered depths (CAREFUL/RIGOROUS/PLANNED), the semantic judge and Spring context assembly. So the answer for every row
  below is "no turn-level test"; the column names the closest tests that do exist.
- **Approval cost has dropped.** Phase 1 (approval continuation, `app.approvals.continuation.enabled: true`) now resumes
  the task after a decision, with real-path tests (`ApprovalContinuationE2ETest`, `ApprovalParkedTurnE2ETest`,
  `AgentJobApprovalContinuationE2ETest`). Controls that add approvals (taint enforce, trifecta require-approval,
  unclassified require-approval, SUPERVISED) were much costlier before it. This is the main reason some
  recommendations below are stronger than the audit's.
- No recommendation weakens a current default. Where `personal` already differs from the base, the base is not loosened.

## Notes

1. **Cheapest wins first.** Rows 1 and 2 are inert until used, so enabling them for team and enterprise costs nothing and
   unlocks the feature (saving hooks or policies answers 409 while off). Row 6 enforce and row 10 are the next lowest risk.
   Rows 3, 4, 7 and 5 change what users see and need a measured observe period. Row 11 should not be turned on at all
   until fixed.
2. **Observe before enforce is already built in** for taint (3), pinning (5, warn records pins), supply chain (6, scan on),
   trifecta (4, warn) and unclassified tools (7, counter). The decision for each is the duration of the observe period and
   who reads the data, not new code.
3. **Approvals now close the loop**, so the cost of rows 3, 4, 7 and the SUPERVISED tier is a prompt per gated call, not a
   stalled task. **Decision (owner): SUPERVISED no longer needs approval for a read-only call in `personal`, and still
   gates every call elsewhere.** The setting is `app.guardrails.supervised.gate-read-only`: `true` in the base
   `application.yml` (SUPERVISED gates every call, including `web_search`: unchanged, nothing weakened), `false` in
   `application-personal.yml` (one person who is also the approver; every read-only prompt was the main reason a task felt
   stalled). It is a security key in the settings catalog (`guardrails.supervised.readOnlyCalls`), so a workspace or an
   agent can only choose the stricter `gate`. With it `false`, a call is let through without a person only when ALL hold:
   the tool has an explicit classification row that says read-only (never an unclassified tool, never an MCP server's own
   read-only hint), the agent is positively judged not to hold the lethal trifecta, and nothing else asks for approval
   (taint, a procedure, a hook, the confirmation gate). Argument policies, hooks, budget and step limits and the circuit
   breaker still run on it, and each such call is audited (`tool.supervised.auto_allowed`) and journaled as `auto-allowed:
   read-only under SUPERVISED`. What this does NOT lift: `remember_fact` is classified as a write (`WRITE_TENANT`), so it is
   still asked about; an agent that holds the trifecta keeps full gating (row 4 `require-approval` therefore still means
   every call is gated for such an agent in every profile); an Auto-select agent is judged by the trifecta analysis only
   with `trifecta-analyse-auto-select` on. Team and enterprise keep the base value `true`; flip it per deployment with
   `APP_GUARDRAILS_SUPERVISED_GATE_READ_ONLY` once the audit rows have been read. Test: `SupervisedReadOnlyE2ETest`.
4. **Personal stays light on purpose.** One person is also the approver and the model is small: keep depth FAST, pinning in
   warn, trifecta in warn, hooks and policies off (nobody authors them), and rely on taint enforce plus the OS sandbox,
   which are already on. The only personal change recommended is row 10 (compaction) and the job step journal in row 12.
5. **Evidence gap applies to all 16 rows.** Every "flip" should land with a harness test that sets the control on and
   drives a turn; today a green unit suite says the component works in isolation, not that a turn uses it.
6. **Not verified.** Nothing was built or run for this document. Test names come from the repository, not from reading
   each body; costs are structural (calls per turn), not measured; "team" and "enterprise" are described, not shipped
   profiles; I did not check whether row 12's tests touch a real Postgres or whether row 13's proposals are per-user.
