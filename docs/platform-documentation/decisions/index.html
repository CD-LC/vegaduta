Architecture Decision Records — Index & Process

An ADR is the permanent record of one consequential architecture choice: the problem, the decision, the alternatives that lost, and the consequences — including the incidents that motivated or followed it. This index lists every ADR for the VegaDūta platform in the format of Michael Nygard's Documenting Architecture Decisions.

When to write an ADR

Write one when a decision meets any of these tests:

  • Hard to reverse. Data models, tenancy isolation, provider/hoster choice, secret stores — anything whose undo cost is a migration, not a config edit.
  • Crosses module or service boundaries. Contracts other modules or satellite services depend on (e.g. "ChatClients are built per request", "secrets resolve at revision creation").
  • A real incident taught it. Most ADRs here exist because something broke: the PgBouncer wrong-tenant routing (ADR-0002), the 401-everything issuer mismatch (ADR-0005), the "Cookie not found" domain-cutover outage (ADR-0007). The record exists so the next contributor doesn't have to re-learn it.
  • A competent engineer would ask "why is it like this?" If the answer is non-obvious and lives only in someone's memory or a closed chat, it is an ADR.

Do not write an ADR for reversible implementation detail, library minor-version bumps, or anything already fully expressed by code + tests. Ops events belong in runbooks and postmortems; the ADR cites them, it does not replace them.

Lifecycle

StateMeaningBadge on this site
ProposedWritten for review; not yet binding. An ADR should not sit here long — decide it or withdraw it.proposed
AcceptedBinding. Code, deploy files and docs that contradict it are bugs.accepted
DeprecatedNo longer holds; kept for history with the reason recorded.deprecated
SupersededReplaced by a newer ADR, which must be linked in both directions.superseded

An accepted ADR is edited only to add dated clarifications or a supersession link — never silently rewritten. If the world changed, write the new ADR and mark the old one superseded; the diff between them is the history.

Format

Each ADR page follows the Nygard structure, extended with two sections this platform found it needs:

Status line
Lifecycle badge, decision date, deciders, supersession links.
Context
The problem and the forces: team size, cost, operational constraints, the incident at hand.
Decision
The choice, stated as a commitment in active voice.
Alternatives considered
A table of the options that lost and why — this is what makes the record a decision rather than a description.
Consequences
Positive and negative, honestly split — including consequences that only showed up later in real use.
Evidence & references
Repository paths and commits the claims can be checked against.

Using the template

There is no separate skeleton file — the newest ADR page is the template. To add one:

  1. Copy docs/platform-documentation/decisions/adr-0009-untrusted-code-sandboxing.html to adr-NNNN-short-slug.html with the next free number.
  2. Update <body>'s data-doc (next VD-ADR-0NN), data-page and data-updated; fill the Status/Context/Decision/ Alternatives/Consequences/Evidence sections.
  3. Add a row to the index table above and a nav entry in assets/js/site.js under the decisions section.
  4. Number sequentially — ADR numbers are never reused, even if a record is withdrawn.
