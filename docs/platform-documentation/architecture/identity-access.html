Identity & Access (Keycloak)

Keycloak 26 is the platform's identity provider. Every API call into core is authenticated as an OAuth2 resource-server request against realm agentic-ai; tenancy itself is derived from the JWT's tenant_id claim. The subtle part is not OAuth — it is that core must accept tokens from two issuer URLs for the same realm, and that realm import files drift from the live realm.

3. The dual-issuer requirement

Removing KEYCLOAK_ADDITIONAL_ISSUERS 401s everything

Core validates tokens against two issuer URIs for the same realm: KEYCLOAK_ISSUER_URI (the raw/internal issuer — historically localhost:8180 or the container DNS name) and KEYCLOAK_ADDITIONAL_ISSUERS (the public issuer, https://auth.example.com/realms/agentic-ai). Browser-issued tokens carry the public issuer; internal flows carry the raw one. Both must be configured — never "fix" one into the other. If either is missing, that whole class of tokens fails with 401 on every endpoint.

Token validation additionally enforces an allowed-azp list: only tokens issued to the registered clients above are accepted. JWKS is fetched internally from http://keycloak:8080 (compose DNS or the in-cluster Service), not through the public domain: a CDN or WAF in front of auth.<your-domain> may block Python user agents and break the Python services' key fetch.

4. User management and signup

  • Signup: /api/signup creates the Keycloak user and provisions the tenant schema in one flow.
  • Admin operations: user management goes through the Keycloak Admin REST API via KEYCLOAK_ADMIN_BASE_URL (core/admin module's KeycloakAdminClient).
  • unmanagedAttributePolicy=ADMIN_EDIT is mandatory. Without it, Keycloak drops non-mapped user attributes — including tenant_id — and every token for that user silently loses its tenant claim, which then breaks tenant resolution downstream.
  • Post-import reconcile scripts exist because realm imports do not fully reproduce the live realm — run them after any realm re-import.
Realm JSON ≠ live realm

deploy/keycloak/agentic-ai-realm.json is a provisioning artifact, not a mirror. Known drift: identity providers (GitHub/Google/ Microsoft) are enabled in the live realm but carry placeholder IDs in the JSON. Trust the live realm for "what is configured"; trust the JSON for "what a fresh environment gets" — and reconcile after imports.

5. Security configuration

  • SecurityConfig runs under profile !insecure — the insecure profile exists for local/test use and must never reach an environment.
  • The app fails closed: with neither the secure nor the insecure profile, authentication is still enforced — there is no configuration mistake that silently opens the API.
  • Route-level rules include /api/platform/** → ROLE_platform-admin; webhook paths are opened per-channel with their own signature validation instead of JWT auth.
