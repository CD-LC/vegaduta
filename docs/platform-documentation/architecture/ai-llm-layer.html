AI / LLM Layer

The AI layer is the heart of the platform: a Spring AI 1.1.7 stack that talks to fourteen LLM providers under two credential regimes (tenant BYOK and a platform-hosted pool), wraps every call in metrics, budget, guardrail and tracing advisors, and deliberately disables almost everything Spring AI would auto-configure. Everything on this page was verified against core/chat/, core/providers/, core/agents/, core/mcp/, core/mcpserver/ and core/pom.xml.

Critical design: auto-configuration is the enemy

CoreApplication excludes eleven Spring AI auto-configurations — Anthropic chat; OpenAI chat, embedding, image, speech, transcription and moderation; GoogleGenAI chat and both embedding configs; and ToolCallbackConverterAutoConfiguration. The reason is fundamental: every ChatClient is built per-request from that tenant's decrypted credentials. A singleton auto-configured client would pin one API key (or none) for the whole JVM — wrong for a multi-tenant BYOK platform, and a boot-time crash when no key is present. The ToolCallbackConverter exclusion additionally stops outbound MCP tools from leaking into the inbound MCP server — without it, the server published the tenant's outbound tool set to external MCP clients. It was removed once, broke the curated-tool contract, and was re-excluded immediately (2026-08-15, documented in CoreApplication's javadoc).

One OpenAI-compatible engine, many providers

Grok, DeepSeek, OpenRouter, Groq, Mistral, Meta, Sarvam and Ollama all reuse Spring AI's OpenAiApi with a custom baseUrl (and, for Sarvam, a custom auth header). That reuse is exactly why their parameter quirks — stop, stream_options, penalties — had to be discovered provider-by-provider in real traffic and are now handled in each factory rather than assumed by the shared client.

3. Credential model — BYOK and the hosted pool

There is exactly one encryption chokepoint: EncryptionService (core/crypto), AES-256-GCM, keyed by APP_ENCRYPTION_KEY (a base64-encoded 32-byte key). Rotation is supported via APP_ENCRYPTION_KEY_PREVIOUS. If the key differs between any two places core boots, every stored credential becomes undecryptable.

Credential kindStorageResolution
Tenant BYOK LLM keysPer-tenant LlmProviderCredential rows in the tenant's own schema, AES-256-GCM encryptedProviderCredentialResolver, per call — never cached, plaintext never logged
Hosted pool keysplatform_hosted_llm_provider rows in the control plane (public)Managed only via POST /api/platform/hosted-llm-providers — the endpoint encrypts on write
Sarvam / ElevenLabs / Jev keysOwn credential tables (not LlmProviderCredential)Own services — e.g. ProviderCredentialResolver branches SARVAM to SarvamCredentialService
Never raw-INSERT a hosted pool row

api_key is encrypted by EncryptionService on the way in. A hand-written SQL INSERT produces a row that cannot be decrypted and fails at call time with an unhelpful error. Use the platform-admin API. A per-provider ProviderValidator verifies the key on activation, and the plan gate plan_limits.byok_allowed (seeded false for FREE) controls whether a tenant may bring keys at all.

4.1 The registry and factories

ChatClientRegistry dispatches ProviderName to one factory class per provider (e.g. AnthropicAgentChatClientFactory). Every factory-built client gets the same advisor stack:

  • LlmMetricsAdvisor — implements both CallAdvisor and StreamAdvisor. Records latency and call counts, writes the durable llm_call_log row, computes cost via LlmPricingCatalog, and restores TenantContext across Reactor thread hops on streamed calls.
  • DefaultAgentAdvisor beans — includes RlTrajectoryAdvisor (per-turn trajectory recording for the RL subsystem).
  • Hosted-only advisors — FreeTierTokenTrackingAdvisor and PerUserBudgetTrackingAdvisor run only on pool calls.

Two shared pieces of plumbing deserve note: ResilientToolCallingManagerFactory gives every client a tool-calling manager in which a malformed tool call cannot kill a turn, and AnthropicProviderCachingStrategy (with Gemini, OpenAI, Azure and Mistral siblings behind ProviderCachingRegistry) manages prompt caching per provider.

4.2 The hosted-pool fallback chain

When ChatClientResolver selects the pool (FREE tenant or usePlatformLlm), FreeTierChatClientService walks an ordered chain of platform_hosted_llm_provider rows ranked by HOSTED_POOL_ORDER_BY_COST, observed latency, and admin-assigned priority. HostedProviderHealth circuit breakers skip rows that are failing. A wholly failed chain surfaces to the user as a generic chat failure — when debugging, check all rows, not just priority 0.

streamUsage gap — fixed 2026-09-25

Streamed OpenAI-compatible calls were missing stream_options.include_usage, so streamed responses arrived with no usage object and llm_call_log / budget reconciliation recorded 0 tokens for those calls. .streamUsage(true) is now set wherever the upstream accepts it; Meta, Sarvam and Mistral are excluded because they reject the parameter. Any historical token/cost report that predates the fix undercounts streamed calls on OpenAI-compatible providers.

5. The LLM gateway — pre-flight governance

Before any provider call, LlmGatewayService (core/chat/gateway/) runs the pre-flight chain: rate limiter → budget service → content policy → PII redactor → audit service. Its state lives in five tables: LlmGatewayPolicy, LlmGatewayUserPolicy, LlmGatewayUsageLedger, LlmGatewayAuditLog and LlmGatewayPiiAuditLog. A refusal or budget denial happens before the call — which is why "no llm_call_log row" is a valid debugging signal, not a bug.

Non-FAST depths run through BufferedTurnRunner (they cannot stream mid-verification).

Tool resolution and the guarded pipeline

AgentToolProvider.resolveToolsFor assembles the toolset per turn from resolvers: integrations, knowledge (gated by the agent's knowledge profile and flag), browser, the MCP registry, commerce (payment links), and the imagegen / documentgen / sdlc / codeintel / google / sarvam generators, plus call_agent, a2a and progress tools. Every tool is wrapped in GuardedToolCallback inside LoggingToolCallback, and executes in this order:

  1. Step ceiling — a shared AtomicInteger bounds tool calls per turn.
  2. Optional RIGOROUS pre-verify — the independent verifier can reject a call before it runs.
  3. HITL gate — tools matching mcp_tool.* policy go through ApprovalPolicyService + ApprovalReplayGrant.
  4. ToolCallOutputValidator — validates the result shape.
  5. sanitizeToolOutput — strips content the model should not see verbatim.

7. Session memory

Conversation memory is Redis-backed: MessageHistoryAdvisor rehydrates prior turns, persisted through RedisMessageStore and RedisChatSessionStore, with SessionSummarizer compacting long sessions. This is why Redis loss degrades continuity but never loses durable data — the system of record is Postgres.

9. Supporting subsystems

Autonomous jobs

Scheduled/event agent runs are durable QUEUED rows with run-now-mode enqueue on the API pods, cron schedules, event triggers, approval parking, boot-time reconciliation of orphaned rows, and a structured output contract enforced by JobResultSchemaValidator. Progress notes stream back to the session.

Jev — the calibrated decision model

JevDecisionService wraps a TypeSafe-calibrated yes/no model used for two hot decisions: AgentRelevanceSelector (which agent should reply on a shared channel) and QueryComplexityClassifier (per-turn cost routing — deterministic checks first, Jev as rescue-only, fail-toward-primary). Jev uses its own BYOK credential and tenant policy, with a per-agent threshold; precedence is agent > tenant > platform flag.

Knowledge / RAG

Per-tenant pgvector vector_store plus hierarchical knowledge_document tables. The Python sidecar does chunking, embedding, OCR, transcription and reranking. KnowledgeSearchService runs hybrid retrieval — vector similarity + Postgres full-text search fused by Reciprocal Rank Fusion (RRF_K=60) — capped at rag.max-results=20 / rag.max-chars=8000 per turn. Ingestion jobs and Notion / SharePoint / web-crawl connectors feed the base; graphmemory adds Apache AGE multi-hop Cypher recall as a tool.

10. Tracing and the durable call record

Core exports OTLP spans to Langfuse:

OTEL_EXPORTER_OTLP_TRACES_ENDPOINT = http://<langfuse-web>/api/public/otel/v1/traces
LANGFUSE_OTEL_AUTH_HEADER          = <Basic …>   (a secret: env var or Kubernetes Secret)
TRACING_SAMPLING_PROBABILITY       = 0.1           (10% sampling by default)

llm_call_log.trace_id is the Langfuse trace id — the join key between cost accounting (SQL) and prompt/tool detail (Langfuse). Spring AI's built-in observations light up via micrometer-tracing-bridge-otel. Tracing fails silently: a wrong endpoint or stale header drops spans but never breaks calls, so absence of traces is not evidence of absence of calls.

Queries worth memorising

SET search_path TO <tenant_schema>;

-- last 20 calls, newest first
SELECT started_at, provider_name, model, success, latency_ms,
       total_tokens, estimated_cost_usd, left(error_message, 80) AS err
FROM llm_call_log ORDER BY started_at DESC LIMIT 20;

-- today's failures, grouped by cause
SELECT provider_name, model, exception_type, count(*), max(started_at)
FROM llm_call_log
WHERE success = false AND started_at > now() - interval '24 hours'
GROUP BY 1,2,3 ORDER BY 4 DESC;

-- spend and volume by model, last 7 days
SELECT model, count(*) AS calls,
       sum(total_tokens) AS tokens,
       round(sum(estimated_cost_usd), 4) AS usd
FROM llm_call_log
WHERE started_at > now() - interval '7 days'
GROUP BY 1 ORDER BY usd DESC NULLS LAST;

-- p50 / p95 latency by provider
SELECT provider_name,
       percentile_cont(0.5)  WITHIN GROUP (ORDER BY latency_ms) AS p50,
       percentile_cont(0.95) WITHIN GROUP (ORDER BY latency_ms) AS p95,
       count(*)
FROM llm_call_log WHERE started_at > now() - interval '24 hours'
GROUP BY 1;

-- one conversation, in order
SELECT started_at, model, success, total_tokens, trace_id
FROM llm_call_log WHERE session_id = '<session>' ORDER BY started_at;
Debugging one bad call, in order
  1. Get identifiers: approximate time, agent, conversation; the req= id from app logs.
  2. Find the row: SELECT * FROM llm_call_log WHERE request_id='<req>' OR session_id='<s>'.
  3. Read success, exception_type, error_message — usually ends it.
  4. success = true but wrong answer → Langfuse via trace_id.
  5. No row → the call never reached a provider: on-device/WebLLM path, guardrail refusal, budget cap, or earlier auth/tenant failure.
  6. Many rows failing at once → check the pool, not the tenant.
