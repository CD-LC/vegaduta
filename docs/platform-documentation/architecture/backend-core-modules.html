Core Module Catalogue

The backend is a modular monolith: core/pom.xml is a pure aggregator/BOM (packaging=pom, no source of its own) over 40 Maven modules plus two auxiliary components (mcp-data, mcp-stdio-proxy), assembled into one Spring Boot deployable (core/app) and two specialised assemblies (app-worker, app-jobs). Maven itself enforces the dependency boundaries — a module that reaches across a boundary is a compile error, not a code-review nit. Descriptions below are taken from each module's own pom.xml.

Module catalogue

Platform, tenancy & infrastructure

ModulePurpose
securityKeycloak OAuth2 resource-server config, TenantContext + servlet filter. Leaf.
tenancyTenant/AppUser entities, schema-per-tenant Hibernate multi-tenancy, signup/provisioning, Flyway migration-per-schema. Depends on admin, billing, security, storage.
adminKeycloak Admin REST client for user management (UserAdminController). Depends on audit, security.
platformCross-tenant "Ecosystem Maintenance" API for super-admins: hosted LLM pool, plan overrides, platform observability, health/metrics aggregation. Gated by /api/platform/** → ROLE_platform-admin.
billingBilling-gateway abstraction (Razorpay adapter) + GST invoicing, used by hosted operators; plan gating is off by default (NEXT_PUBLIC_BILLING_ENABLED). Depends only on security.
cryptoEncryptionService — AES-256-GCM at-rest encryption for provider keys and channel tokens. JDK javax.crypto only; leaf.
secretsConsumer secrets vault: named encrypted secrets referenced as {{secret.NAME}}, resolved only inside the tool-execution boundary.
storageFileStorageService — S3-API object storage (SeaweedFS in the Full tier, local disk in Lite, or any S3 API via config). Leaf.
eventbusKafka-backed event backbone (WorkflowEvent envelope, transactional outbox, relay). Inert unless configured; depends only on tenancy.

Agent runtime & LLM

ModulePurpose
agentsAgent entity + chat orchestration and the tool-call plumbing (old "tools" package) in one module — a verified circular dependency (AgentToolProvider needs Agent; AgentChatService needs AgentToolProvider) made splitting them a real code change.

mcpserverInbound MCP hosting: exposes a curated tenant tool set (call_agent, call_workflow, search_knowledge) to external MCP clients over STREAMABLE HTTP at /mcp.
codeintelCode-intelligence ToolCallbacks: search a tenant's indexed codebase, walk its deterministic code graph, get cited answers. Thin HTTP client over the code-intel service.
sdlcE2B sandbox integration scaffold: E2bCredential BYOK storage + E2bSandboxClient (create/list/kill sandboxes). Leaf-shaped; no tool callbacks yet.

Governance & quality

ModulePurpose
guardrailsTool step ceiling, allow-list, output sanitisation, GuardedToolCallback; content-moderation policy packs, external-classifier seam, human review queue. Depends on approval, audit, tenancy.
auditAudit log: AuditLogEntry/Service/Controller. Leaf.
evalStandalone golden-dataset prompt-regression CLI harness. Deliberately touches no DB or tenant context; runs in its own CI workflow, never in mvn verify.
qualityAgent response quality scoring across dimensions (helpfulness, accuracy, tone, length, relevance, safety) with historical trend tracking.
rlIn-core RL subsystem: reward capture, per-turn trajectory recording, contextual bandit (Thompson sampling over Beta posteriors) for safe non-side-effecting choices.
sharingCross-user resource sharing: resource_grant table + ResourceAccessService (RUNNER/VIEWER/EDITOR, anti-enumeration 404-on-denial). No dependency on agents/workflow — owner lookup goes through a ResourceOwnerLookup SPI.

Media, channels & integrations

omnichannelChannel adapters and inbound webhooks (Twilio WhatsApp/SMS/voice, Meta, Telegram, Slack, Discord, Teams, email), channel sessions/pairing, operator handoff, signature validation.

imagegenImage generation (Flux / GPT-Image) with own entity/service/controller/tool-callback surface.

googleGoogle Workspace: one platform-level OAuth app (Drive/Gmail/Calendar/Sheets), per-tenant encrypted refresh tokens.

Assemblies & auxiliary

ModulePurpose
appThe Spring Boot application: CoreApplication, cross-cutting glue (GlobalExceptionHandler, WebConfig), application*.yml and db/migration/**.
app-configShared Spring configuration resources (application.yml + profile files) for every executable assembly.
app-workerTemporal workflow-worker deployable: same modules via app-config, booted as WorkerApplication — no REST controllers, no @Scheduled, no Flyway.
app-jobsBackground-jobs deployable: JobsApplication — no REST controllers, @Scheduled ON, no Flyway, no per-tenant startup work.
templatesCommunity template gallery: sanitised moderated catalogue of agent/workflow designs (community_template, control-plane schema).
mcp-dataAuxiliary MCP data component (not in the main reactor build).
mcp-stdio-proxyNode.js sidecar that executes dynamic STDIO MCP servers outside the JVM (MCP_STDIO_SIDECAR_* envs).

REST surface — controller distribution

Approximately 193 @RestController classes ship in the core assembly. The distribution is deliberately uneven — channel and agent administration dominate:

Why "common" is not a module

GlobalExceptionHandler and WebConfig live in app, not a shared module: the exception handler has an @ExceptionHandler for nearly every module's custom exceptions — it depends on almost everything and nothing depends on it. That is cross-cutting glue, not shared low-level code.

Dependency rules that will bite you
  • New capability = new leaf module depending on crypto/security/tenancy only — the established "sarvam shape". Nothing upstream may depend back on it.
  • providers → sarvam is a real dependency (credential resolution); the reactor builds sarvam first regardless of <modules> order.
  • agents and tools are merged — do not attempt to re-split without breaking the verified AgentToolProvider↔AgentChatService cycle first.
  • eval is a true standalone leaf — never let it gain a dependency on tenancy or the database.
