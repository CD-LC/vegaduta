System Architecture

VegaDūta is a modular monolith — one Spring Boot 3.4 / Java 21 deployable assembled from ~42 Maven modules — surrounded by a small set of satellite services for the work a JVM should not do (Python ML, untrusted-code execution, voice) and the work frontends do (two Next.js consoles). This page is the layered view; Service Topology is the deployment view.

Why a modular monolith

The choice is deliberate and documented (ADR-0001): the team's constraint was deployment operability and data-consistency under multi-tenancy, not service-count. One JAR gives a single Flyway migrator, a single security context, in-process calls between agent / workflow / tenancy logic, and one artifact to build, scan and roll back. The module boundaries are drawn so a later extraction is possible — the deployment-shapes work (below) already splits background work onto separate JVMs without splitting the codebase.

What is not in the monolith is equally deliberate: anything that executes untrusted code (MCP STDIO packages, tenant-authored code), the Python ML stack, and the per-channel bridges live in satellites so core's process boundary is also its trust boundary.

The three deployable assemblies

AssemblyMain classRunsNotes
core/app CoreApplication The HTTP surface — all ~193 REST controllers, SSE/AG-UI streams, webhooks — plus, in a single-process deployment, every scheduled job too The core image; the only assembly in the Lite tier and the default Full tier (port 8080)
core/app-worker WorkerApplication Temporal workflow worker — executes durable workflow activities Defined and built (core/pom.xml); gated by app.workflow.temporal.worker-enabled; no @EnableScheduling. Runs as core-worker with Compose profile temporal or Helm global.temporal.enabled.
core/app-jobs JobsApplication The ~30 scheduled sweeps — job dispatch, outbox relays, channel pollers, quota resets Its own application-jobs.yml; runs as core-jobs with Compose profile jobs or the Helm chart deploy/helm/charts/core-jobs (global.components.coreJobs, default on).

The same split also exists inside one image as Spring profiles: shape-api (serve traffic, skip the sweeps) and shape-jobs (run the sweeps, skip request-serving concerns), defined in core/app-config. With neither profile set, one JVM runs everything — which is what the Lite tier and the default Full tier do: the single core container serves requests and runs the sweeps.

How the two canonical flows traverse the layers

A console page load

Browser
  → Caddy (Compose domain overlay) or Kubernetes Ingress, TLS for *.<your-domain>
    → web (Next.js, server-rendered)

Browser (client-side JS)
  → api.<your-domain> (or localhost:8080) → core:8080
    → pgbouncer:6432 (Full tier, session pooling)
      → postgres:5432 (bundled) or your managed PostgreSQL

Core reaches the database through compose DNS (DB_HOST/DB_PORT); internal service names such as pgbouncer and keycloak:8080 are correct and must not be "fixed" to public URLs.

An agent turn

core → guardrails
     → tool resolution (MCP + custom code + built-ins)
     → LLM provider (tenant BYO key, or the platform hosted pool)
     → LlmMetricsAdvisor → llm_call_log row (in the tenant's schema)
                         → OTLP span → Langfuse (profile tracing, optional)

Identity at a glance

Keycloak 26, realm agentic-ai. Clients — verified from the checked-in realm JSON: agentic-ai-web (public, browser PKCE), agentic-ai-core (confidential; the only client that can mint a token from username + password via direct-access grants), agentic-ai-platform-admin, agentic-ai-mobile, agentic-ai-app, agentic-ai-ide (the last three are reserved for external clients that are not part of this repository). Realm roles: tenant-admin, platform-admin, agent-builder, delegated-user, end-customer. Because Keycloak pins its hostname, core validates tokens under a dual issuer: it validates the issuer Keycloak stamps (PUBLIC_AUTH_URL/realms/agentic-ai), and KEYCLOAK_ADDITIONAL_ISSUERS adds others, for example the old issuer during a domain change. See Identity & Access.

Off by default
  • Core's code-intel bridge (code-intel.enabled=false by default; needs CODE_INTEL_* env to enable).
  • The Kafka event bus (Redpanda) — only with Compose profile events or temporal; the workflow Spring profile needs it.
  • app-worker and app-jobs as separate processes — the assemblies exist; Lite and the default Full tier run everything in the one core container.
