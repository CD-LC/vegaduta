The two architectural facts that explain most surprises

1 · Schema-per-tenant

Every tenant is a Postgres schema, resolved from the request's tenant context via SET search_path. Shared platform state lives in the control-plane schema. The hard consequence: PgBouncer must run in session pooling mode — transaction pooling hands a connection mid-session to another tenant's search_path and reads the wrong tenant's data. The Full Compose tier runs PgBouncer as the pgbouncer service on port 6432, configured for session pooling.

2 · One Flyway version namespace

Migrations live in two directories — core/app/src/main/resources/db/migration/controlplane/ (shared, once) and …/tenant/ (per schema) — but they are validated as a single version space. A controlplane/V227 and a tenant/V227 collide even though the folders differ. Before picking a number, check the maximum in both folders; scripts/ci/flyway-lint.sh is the CI gate that catches collisions.

Request path, in two sentences

A browser hits Caddy or your Ingress → web (server-rendered); the page's client JS then calls api.<your-domain> (or localhost:8080) → core:8080 → PgBouncer → Postgres. An agent turn inside core runs guardrails → tool resolution (MCP / custom code / built-ins) → the tenant's BYOK provider or the platform pool → LlmMetricsAdvisor, which writes an llm_call_log row and emits an OTLP span to Langfuse when tracing is on.
