Webhooks & Callbacks

Inbound base
https://api.example.com/webhook/** and /api/billing/webhook/** (public URL that providers call).
Spring Security
permitAll by design: third-party servers cannot present a Keycloak token. Each controller authenticates the payload itself. See Authentication.
Outbound
Tenant-managed subscriptions at /api/webhooks (HMAC-signed, retried).
Delivery model
Providers are at-least-once; core de-duplicates on provider ids or content hashes before acting.

Inbound processing pattern

sequenceDiagram
  participant P as Provider
  participant W as Webhook controller
  participant T as TenantResolutionService
  participant D as Dedup (Redis)
  participant S as AgentChatService / workflow
  P->>W: POST /webhook/... (signature or secret)
  W->>T: resolve tenant from provider account id
  W->>W: verify signature with tenant credential
  W->>D: claim delivery id
  D-->>W: new or duplicate
  W->>S: run agent turn / trigger workflow
  W-->>P: 200 (fast)

Tenant is resolved from the provider's account identifier (bot id, phone-number id, team id, and so on) through the control plane, then TenantContext is set to that schema. Deep behaviour per channel is in Channels & Omnichannel.

Inbound: workflow webhook triggers

PathCredentialBehaviour
POST /webhook/workflows/{token}The secret {token} itself (SHA-256 hashed for lookup); one token per Trigger nodeUnknown token or disabled node: 404. Node not in shared-secret auth mode: 409. Workflow not ACTIVE: 409. Redelivery: 409. Success: 200 with the run (WorkflowRunResponse). JSON body is optional; it becomes the run input.
POST /webhook/workflows/oidc/{workflowId}Authorization: Bearer <jwt> with a tenant JWT whose realm_access.roles contains workflow-trigger503 if no JWT decoder (security profile off). Missing bearer or invalid token: 401. Role or tenant problems: 401/403 per the controller.

De-duplication on the token path uses the first of X-Delivery-Id, X-Webhook-Id, X-Request-Id that the sender provides, else a SHA-256 of the body, scoped by trigger node. The workflow-trigger role is a realm role that is not auto-provisioned; it must be assigned to a service account in Keycloak. Tokens are created and revoked through GET/POST/DELETE /api/workflows/{workflowId}/nodes/{nodeId}/webhook (PERM_MANAGE_WORKFLOWS_ADMIN). See Workflow Engine.

Event types (catalogue)

workflow.run.started|completed|failed|cancelled|resumed, workflow.node.completed, workflow.output.emitted, approval.requested, approval.resolved, approval.execution.recorded, document.generation.completed, an agent-reply-completed event (payload includes agentId, sessionId), inbound-channel-message events (Discord, X, Telegram, email and Teams entries were read; earlier entries in the catalogue were not), and webhook.test. Use GET /api/webhooks/event-types for the authoritative list on a deployment.

Delivery contract

  • HTTP POST, Content-Type: application/json, User-Agent: VegaDuta-Webhooks/1.0; connect timeout 5 s, request timeout 15 s; redirects are never followed (a 3xx is a failure).
  • Headers: X-VegaDuta-Event, X-VegaDuta-Delivery (delivery id), X-VegaDuta-Signature: t=<unix>,v1=<hex> where v1 = HMAC-SHA256(secret, "<t>.<raw body>").
  • Any 2xx marks the delivery DELIVERED; anything else retries with exponential backoff (30 s doubling, capped at 30 min) up to 10 attempts, then DEAD. At-least-once: receivers must be idempotent (use X-VegaDuta-Delivery).
  • The target URL passes the same SSRF guard as remote MCP URLs at save time and again at send time.
  • The JSON body envelope is not specified on this page (payload shape per event is not documented in the repository beyond the catalogue descriptions).
# verify (pseudo): reject if abs(now - t) is large, then compare
expected = hex(hmac_sha256(secret, t + "." + raw_body))
constant_time_equal(expected, v1)
