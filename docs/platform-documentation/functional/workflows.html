Workflow Engine

Workflows orchestrate agents, deterministic steps and human checkpoints as a versioned graph. A definition is the edited artifact; a run is one durable execution of a version. The engine lives in core/workflow and offers two execution modes behind one definition format.

stateDiagram-v2 [*] --> DRAFT: definition saved (canvas, autosave) DRAFT --> VERSIONED: publish (immutable version) VERSIONED --> RUNNING: trigger (manual / webhook / schedule / channel) RUNNING --> WAITING_APPROVAL: approval node or gated step WAITING_APPROVAL --> RUNNING: approve → resume (WorkflowApprovalResumeException path) WAITING_APPROVAL --> FAILED: reject RUNNING --> FAILED: node error edge exhausted RUNNING --> COMPLETED FAILED --> RUNNING: run recovery job
Workflow definition and run lifecycle.

FR-WF-01 · Definitions, runs & the two engines

A definition is a node graph (nodes + edges + per-node payload). Runs are executed by one of two engines, selected by the app.workflow.execution-engine setting:

EngineImplementationWhen to use
Synchronous engine WorkflowExecutionEngine / OrchestratorService — in-process execution inside core/app. Default; simple deployments, short-lived runs, staging.
Temporal durable engine TemporalWorkflowExecutionEngine + WorkflowRunWorkflowImpl — runs are Temporal workflows with replay durability. Long-running runs, crash-proof human-in-the-loop pauses, production durability.

Both engines honour the same definition format, node catalogue and approval semantics; the choice is operational, not a different feature set. See ADR index for the Temporal adoption context.

The node executor (WorkflowNodeExecutor) dispatches on node type. The catalogue:

Trigger and terminal nodes count toward the 18-type catalogue. The authoritative list is the dispatch in core/workflow/.../WorkflowNodeExecutor.java; names above are functional labels, not wire enums.

FR-WF-03 · Versions & run diff

Publishing a definition creates an immutable version; runs pin to the version they started on. Run diff (migration V273) compares two runs — or a run against its version — to show which nodes executed, what each produced, and where executions diverged. This is the debugging primitive for "why did this run behave differently".

FR-WF-04 · Error handling: per-node error edges & retry

A node can declare an error edge: instead of failing the run, a failing node routes to a handler branch. Retry policy is per-node (attempt count, backoff). If retries exhaust and no error edge exists, the run fails and becomes eligible for the recovery job (FR-WF-09).

FR-WF-05 · Triggers

Runs start from four trigger surfaces: manual launch from the canvas/API, webhook trigger nodes (external systems POST in), schedule trigger nodes (cron), and channel trigger nodes (an inbound WhatsApp/Telegram/etc. message starts a run — see VD-FN-003 for inbound routing). Webhook event types are catalogued in core/eventbus/.../WebhookEventCatalog.java.

FR-WF-07 · Canvas UX

The web-admin canvas is the authoring surface: drag nodes, wire edges, configure per-node payloads. Undo and autosave make editing safe — drafts persist without an explicit save and publish is a separate, deliberate action that mints a version.

FR-WF-08 · Approval pause / resume

When a run reaches an approval node (or a gated action inside it), the engine raises WorkflowApprovalResumeException — the mechanism that parks the run with its full context. The approval appears in the tenant's approval inbox; on approve, the run resumes from the parked node with the decision recorded; on reject, it fails. Approver authorization follows the rules in VD-FN-006 (adminOnly payloads and tool-call approvals are tenant-admin only).

FR-WF-09 · Run recovery job

A scheduled recovery job sweeps for runs stranded by crashes or restarts and re-drives them — the synchronous-engine counterpart to Temporal's built-in replay. Together they guarantee a run is never lost between "triggered" and "terminal state".
