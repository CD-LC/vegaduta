End-to-End Suites

Everything under web/e2e/: the Playwright business-case suite, the smaller TypeScript specs, three Playwright configurations, and the @mvp-acceptance slice that the (currently manual) GitHub workflow runs. The suite header states the convention: a real running core + sidecar + Postgres + Keycloak + Redis stack, no mocking anywhere. Setup detail lives in web/e2e/README.md.

Three Playwright configurations

ConfigTest dirBehaviour as configured
web/playwright.config.js (the business-case suite)./e2e/specsSequential: fullyParallel: false, workers: 1, retries: 0, test timeout 120 s, expect timeout 15 s, action/navigation timeout 15 s. Headed with a 1000 ms slowMo by default; set E2E_HEADLESS=true and E2E_SLOWMO_MS=0 for a fast run. Base URL from E2E_BASE_URL (default http://localhost:3000). Sequential on purpose: shared tenant state and the Redis-backed signup rate limiter.
web/playwright.staging.config.ts./e2eTargets https://app.staging.example.com, 1 retry, 4 workers, longer action timeout (15 s), no web server.
Staging config target

The staging config hard-codes a staging hostname (app.staging.example.com in these docs). Point it at your own staging domain, confirm the target before running it, and never describe a run against it as production-verified.

Design conventions worth knowing

  • Fresh tenant per test via POST /api/signup in web/e2e/fixtures.js; no shared tenant.
  • No real payment is completed; tenant schema is usable at signup independent of any payment step (billing is off by default).
  • Direct-API specs (05, 09, 10) need E2E_KEYCLOAK_CLIENT_SECRET for the agentic-ai-core client via a test-only password-grant helper.
  • Opt-in specs skip rather than fail when their variable is unset: E2E_ANTHROPIC_API_KEY, E2E_TWILIO_*, E2E_SAMPLE_PDF_PATH / DOCX / IMAGE / AUDIO / VIDEO, E2E_ADMIN_BASE_URL, E2E_PLATFORM_ADMIN_EMAIL / PASSWORD. Names only; values are never documented here.
  • Local core needs the e2e Spring profile (add e2e to SPRING_PROFILES_ACTIVE, e.g. security,knowledge,mcp,e2e; core/app-config/.../application-e2e.yml), which raises the signup rate limit; otherwise the sixth signup from one IP fails with 429.

@mvp-acceptance slice and the e2e workflow

Six journeys are tagged in the test(...) title, per the README (six passing-tagged tests; workflow-designer contributes two): signup and login (01), agent-template pre-fill (15), knowledge .md upload and search (04), workflow create as draft and synchronous run (11, two tests), and the web-admin access-restricted negative path (19). A tagged FREE-tier chat journey in spec 02 is recorded as test.fixme, not passing.

flowchart LR A["workflow_dispatch e2e.yml"] --> B["boot-stack composite action: compose + ci overlay, health gate"] B --> C["npm install + playwright install chromium"] C --> D["timeout 900 npx playwright test --grep @mvp-acceptance"] D -->|failure| E["upload traces + service logs"] D --> F["compose down -v"]
  • Job timeout 30 minutes; the Playwright step itself is capped at 900 seconds (15 minutes), the acceptance budget cited in the workflow.
  • Triggers: the nightly cron 0 3 * * * is commented out; the workflow is workflow_dispatch only by default. The job's PR path is gated on a full-stack label if PR triggers return.
  • The workflow's own comment asks a repo admin to mark mvp-acceptance a required check on main; that branch-protection setting is not verifiable from the repository.
Not documented in the repository

Current pass rates, the count of individual test cases, the date of the last full run, and whether the last full run was green are not recorded in the files read.
