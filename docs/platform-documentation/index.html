How to read the verification markers

These pages distinguish what was checked against the code from what is assumed. Throughout this documentation set:

MarkerMeaning
verifiedChecked against the repository on the stated date
unverifiedBelieved true but not re-checked — treat as a lead, not a fact
live / referenceA supported deployment path
draftAuthored but never deployed/applied — aspirational, not real
retiredWas real, no longer is — kept for history
Non-negotiable operating rules
  1. Back up deploy/compose/.env (or your Kubernetes Secrets) together with the data. APP_ENCRYPTION_KEY must be identical everywhere core boots, or every stored credential becomes undecryptable.
  2. Never point a browser-facing or token-issuer URL (PUBLIC_*) at localhost on a server. Never bake a localhost NEXT_PUBLIC_* into an image you deploy.
  3. The issuer core validates must match the one Keycloak stamps; extra issuers go in KEYCLOAK_ADDITIONAL_ISSUERS — otherwise every token 401s.
  4. A hung service is evidence to collect (logs, container state, memory) before you restart anything; docker compose down -v deletes data.
  5. Pin VEGADUTA_VERSION; read the release notes before scripts/vegaduta upgrade.

Conventions used across every page

  • Every page carries a document ID (VD-XX-NNN), a status badge, and a last-verified date.
  • Commands are copy-paste runnable; <angle-bracket> values must be substituted.
  • Source file paths reference the repository root, e.g. core/chat/pom.xml.
  • Diagrams use Mermaid — an internet connection is required to render them (they degrade to readable source otherwise).
